# DFX测试用例编写指导

## 1. 定义

DFX = Design for X（面向全生命周期设计）
X 代表组件全生命周期的各类非功能维度，DFX 测试就是专项验证系统设计是否满足运维、部署、故障排查、扩缩容、自愈、可观测等非功能能力，区别于普通功能测试（只校验业务逻辑是否走通）。
DFX 测试用例：专门用于校验系统可运维、可观测、可部署、高可靠设计能力的标准化测试用例，不属于功能用例，属于非功能专项集成 / 稳定性测试用例。

**与 FIT 的划分**：以验证目标判定。凡以探针/日志/指标/自愈/性能/安全/兼容为验证目标的用例归 DFX；业务功能正确性（部署就绪、主路径、功能配置变更后业务生效、业务状态迁移、业务级负例）归 FIT。场景归属以 `FIT与DFX场景归属判据.md` 为准，禁止细化复制 FIT 业务场景。

## 2. 常见DFX分类与测试用例设计方法

| 分类         | 全称                       | 简写 |
| ------------ | -------------------------- | ---- |
| 可测试性设计 | Design for Testability     | DFT  |
| 可诊断性设计 | Design for Diagnosability  | DFD  |
| 可运维性设计 | Design for Serviceability  | DFS  |
| 可靠性设计   | Design for Reliability     | DFR  |
| 性能设计     | Design for Performance     | DFP  |
| 安全性设计   | Design for Security        | DFNS |
| 兼容性设计   | Design for Compatibility   | DFC  |

### 2.1. DFT 可测试性设计

**核心验证目标**
组件是否易于自动化测试、易于外部探测、无需侵入改造即可验证状态。

**通用校验点**
- 提供标准化健康探测接口 / health 端点 / 就绪探针
- 提供标准化观测输出（日志/指标/状态接口）
- 支持动态配置生效，无需重启服务（断言**可探测/可外部识别**，不断言业务功能按新配置生效；业务生效归 FIT）
- 输出内容结构化、可机器解析、可自动化断言
- 启动、运行、退出状态可外部识别

**DFT 通用标准用例示例**
用例名称：DFT-验证组件暴露标准化健康探测接口
DFX分类：DFT 可测试性
前置条件：组件容器正常运行就绪
测试步骤：调用组件健康检查端点（如 GET /health）
预期结果：
- 接口返回标准成功状态码（200）
- 组件运行状态可被外部自动化识别
- 满足容器化可探测、可自动化测试设计要求

### 2.2. DFD 可诊断性设计

**核心验证目标**
组件在正常/异常场景下输出足够观测信息，支撑快速定位根因，减少故障 MTTR。

**通用校验点**
- 日志分级规范：INFO/WARN/ERROR
- 异常场景有独立错误日志、错误标识、错误上下文
- 关键行为可观测：启动、加载配置、请求、异常、退出
- 具备异常计数、错误统计、状态指标
- 不出现静默失败、不出现无日志报错

**DFD 与 FIT 非法输入的切分**：构造非法入参只是触发手段。DFD 断言 ERROR 日志、错误上下文、无静默失败、错误指标；「非法输入被 API 校验拒绝、业务错误消息符合规格」归 FIT，不得作为本类用例的唯一断言。

**DFD 通用标准用例示例**
用例名称：DFD-验证组件异常场景可观测可追溯
DFX分类：DFD 可诊断性
前置条件：组件正常运行
测试步骤：构造一次非法入参或故障注入（触发手段），查看日志与状态/指标输出
预期结果：
- 异常行为有明确 ERROR 日志记录
- 日志包含错误原因、触发位置、关键上下文
- 无静默失败、无黑盒异常
- 不将「请求失败/业务拒绝」作为本条唯一预期（该断言属 FIT）

### 2.3. DFS 可运维性设计

**核心验证目标**
组件适配容器化标准运维流程：部署、升级、回滚、配置变更、扩缩容、启停。

**通用校验点**
- 基于 docker-compose 等标准编排部署，服务定义外置
- 支持升级/重建过程无中断、无脏数据
- 配置文件外置，不固化在镜像内
- 支持配置热加载或平滑重启生效（断言运维机制本身；「业务配置变更后功能按规格生效」归 FIT，禁止细化复制为 DFS）
- 支持版本回滚、快速恢复
- 支持水平扩缩实例，无状态冲突

**DFS 通用标准用例示例**
用例名称：DFS-验证组件升级重建无服务中断
DFX分类：DFS 可运维性
前置条件：组件稳定运行
测试步骤：执行 compose 升级/重建，持续观测组件运行状态
预期结果：
- 新旧实例平滑替换，无服务中断、无重启风暴
- 升级完成后服务状态正常
- 符合容器化滚动发布运维规范

### 2.4. DFR 可靠性设计

**核心验证目标**
组件在异常环境、资源波动、进程异常、网络异常下具备容错、自愈、隔离能力。

**通用校验点**
- 进程崩溃、异常退出后可自动重启恢复
- 单任务异常不影响整体服务（故障隔离）
- 网络抖动、超时具备重试/熔断保护
- 资源不足时不雪崩、具备降级保护
- 启动失败可重试、不影响同环境下其他服务

**DFR 通用标准用例示例**
用例名称：DFR-验证组件异常退出后可自愈恢复
DFX分类：DFR 可靠性
前置条件：组件正常运行
测试步骤：手动 kill 组件进程或停止其容器，观察重建与恢复状态
预期结果：
- compose restart 策略 / 守护进程自动拉起服务
- 组件自动恢复运行状态
- 单实例故障不影响同 compose 环境下其他服务

### 2.5. DFP 性能设计

**核心验证目标**
组件资源开销可控、长期运行稳定、高负载不雪崩、无资源泄漏。

**通用校验点**
- CPU/内存占用平稳，无持续递增泄漏
- 高并发/高任务量下不阻塞、不卡死
- 连接、句柄、线程/协程无泄漏
- 处理耗时稳定，无严重性能毛刺
- 支持资源上限控制（limit），不抢占宿主机资源

**DFP 通用标准用例示例**
用例名称：DFP-验证组件长期运行资源无泄漏
DFX分类：DFP 性能
前置条件：组件正常运行
测试步骤：持续运行一段时间，观测容器/进程 CPU、内存变化趋势（docker stats 或服务自身 metrics）
预期结果：
- 内存无持续上涨、无泄漏现象
- CPU 占用平稳，无异常高负载
- 长期运行稳定不重启、不 OOM

### 2.6. DFNS 安全性设计

**核心验证目标**
组件具备身份认证、鉴权、加密、审计等安全机制，能够抵御常见安全威胁，保障数据机密性、完整性与可审计性。

**通用校验点**
- 具备身份认证与访问鉴权机制（Token/mTLS 等）
- 敏感数据传输与存储加密（TLS、密钥管理）
- 关键操作具备审计日志，可追溯
- 输入校验防注入（SQL/命令/路径遍历等）
- 权限最小化，不存在越权与默认高危配置
- 依赖组件无已知高危漏洞

**DFNS 通用标准用例示例**
用例名称：DFNS-验证组件接口鉴权与未授权访问拦截
DFX分类：DFNS 安全性
前置条件：组件正常运行并开启鉴权
测试步骤：使用未授权/无效 Token 调用组件接口，观察响应
预期结果：
- 接口返回鉴权失败状态码（如 401/403）
- 非法请求被拦截，不执行业务逻辑
- 鉴权失败行为有审计日志记录

### 2.7. DFC 兼容性设计

**核心验证目标**
组件在多版本、多环境、多依赖组合下保持功能与接口兼容，升级、对接、共存场景不出现破坏性变更。

**通用校验点**
- 接口向后兼容，版本升级不破坏存量调用方
- 兼容上游/下游多版本依赖（API、配置、数据格式）
- 多语言 SDK 互操作一致（Java ↔ Python A2A-T 互通）
- 多操作系统、多架构（x86/arm）下行为一致
- 升级/回滚过程中新旧版本可短暂共存
- 配置项变更提供兼容策略或废弃说明
- 依赖组件版本变更不影响核心功能

**DFC 通用标准用例示例**
用例名称：DFC-验证组件接口跨版本向后兼容
DFX分类：DFC 兼容性
前置条件：存在 N-1 版本调用方与当前版本组件
测试步骤：使用 N-1 版本客户端调用当前版本组件接口
预期结果：
- 接口字段、协议、行为保持向后兼容
- 调用方无需改造即可正常工作
- 兼容行为可观测、有明确兼容范围说明

**多语言 SDK 互操作示例**
用例名称：DFC-验证Java与Python SDK的A2A-T任务互通
DFX分类：DFC 兼容性
前置条件：Java SDK 客户端与 Python SDK 服务已按 compose 环境启动
测试步骤：使用 Java SDK 向 Python SDK 服务端发起 Task-T 任务
预期结果：
- 任务按 A2A-T 协议正常下发与响应
- 双方对协议原语的序列化/反序列化行为一致
- 无因语言差异导致的字段丢失或语义偏差

## 3. 测试用例字段设计

**核心原则：原子性，可重复性，可追溯性，完整性，独立性**

12 列字段规则如下（表头顺序固定：`case_id,type,module,title,precondition,steps,expected_result,priority,language_profile,component_deps,protocol_primitive,notes`）：

### case_id（必须）

- 编号在仓库范围内唯一
- 格式：`DFX-<模块缩写>-<3位序号>`，如 `DFX-RC-001`（RC = registry-center）；模块缩写与 `module` 列保持一致
- 仅允许中/英文、数字、下划线、连字符，不允许特殊字符与空格
- 典型问题：序号不连续不重号混乱、缩写与 module 列不一致

### type（必须）

- 填该条用例的 DFX 类型简写：`DFT` / `DFD` / `DFS` / `DFR` / `DFP` / `DFNS` / `DFC`
- 一条用例仅对应一种 DFX 类型；与 case_id 中的简写保持一致
- 典型问题：一条用例塞入多种 DFX 断言（应拆分为多条）

### module（必须）

- 被测模块/组件名称：openan 仓名（如 `registry-center`）或仓内模块名
- 与 `case_id` 的模块缩写对应关系保持一致
- 典型问题：描述过于笼统（如只写 `backend`）

### title（必须）

- 简洁表达测试意图，控制在 50 个中文字符内
- 动宾（补）短语，可通过 `_` 追加条件或原因，如 `验证非法payload注册Agent_空名称`
- 建议以 DFX 简写前缀表达意图，如 `验证健康探测端点可被自动化调用`
- 典型问题：名称相互包含、冗余信息、格式不统一

### priority（必须）

- **P0**：核心可观测/可运维主路径（特性验收级非功能能力）
- **P1**：关键诊断与可靠性
- **P2**：扩展 DFX 场景与性能边界（DFX 用例写入本 DFX 表，**不得**混入 FIT 表）
- 建议整体审视级别占比是否合理

### precondition（必须）

- 描述预先配置的环境、数据与系统状态（软件版本、硬件、网络环境）
- **环境要素明确化**：明确 compose 服务组件与版本、端口、metrics 端点、监控工具、预置数据等
- 每一步表述前用序号标识：`阿拉伯数字` + `、`（或空格/半角逗号），从 1 开始
- 前置条件**不是**测试步骤：不含调用接口等操作；步骤数不超过 10 步
- 典型问题：前置条件写成测试步骤、与测试步骤冗余

### steps（必须）

- 每条步骤使用序号标识：`阿拉伯数字` + `、`
- 需要对操作结果进行检查的步骤，结束后加 `见结果N`，N 是 `expected_result` 中的编号
- 每个独立步骤独立编号；连续多个独立步骤不能合并在一个标号中
- 写明操作入口、命令、接口路径与测试参数、观测窗口
- 步骤数建议不超过 10 步
- 典型问题：步骤不可执行、有歧义、缺少命令与参数

### expected_result（必须）

- 每条预期结果使用序号标识：`阿拉伯数字` + `.`
- 禁止二义性、模糊描述；用明确的数据断言：HTTP 状态码、日志级别与关键字、指标名与阈值、health/metrics 端点字段、容器/进程资源数据
- 预期结果与对应步骤编号建议保持一致；一步对应多个结果时用 `见结果N` 说明对应关系
- 描述准确、具体，不出现难以观察和判断的结果
- 典型问题：`功能正常`、`无异常` 之类不可判定的表述

### language_profile（必须）

- 标注该用例自动化执行时使用的语言 profile：`python` / `java` / `js` / `shell`
- 默认取被测仓主语言；跨组件用例取测试落地方（编写测试代码的仓库）语言
- 供 `e2e-test-code-gen` 按 profile 直接消费，写错会导致测试代码生成选错技术栈
- 典型问题：跨仓用例错填被测仓语言、填空

### component_deps（必须）

- 无跨组件依赖时填 `none`
- 有依赖时填 openan 依赖仓（如 `orchestration-center`、`a2a-t-sdk`），多个用 `|` 分隔
- 仅填本用例步骤中真实交互的组件，不为「可能有关」的组件预留
- 典型问题：全部填 none（跨组件用例漏填）、填仓库全限定名带 owner 前缀

### protocol_primitive（条件必填）

- 涉及 A2A-T 协议的用例必填四原语之一：`Task-T` / `Notification-T` / `Negotiation-T` / `Authorization-T`
- 纯 REST API 用例填 `none`
- 典型问题：A2A-T 用例填 none（下游无法生成协议级测试）、发明原语名

### notes（可选）

- 校验点来源（设计文档章节/源码路径）
- `里程碑:vX.Y`：用户指定发布版本时标注；未指定不写
- 材料差异、待确认项、不可自动化原因等补充说明
