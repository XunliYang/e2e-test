# OpenAN测试Checklist

> 版本：v0.1
> 基于：[OpenAN Integration Testing Process and Framework](<OpenAN Integration Testing Process and Framework.md>) v0.1
> 维护：OpenAN集成测试工作组
> 适用：特性需求转测验收（TRR）、版本发布测试
> 术语：FIT（Feature Integration Test，特性集成测试）、SIT（System Integration Test，系统级集成测试）、TRR（Test Readiness Review，特性需求转测验收）、RC（Release Candidate，发布候选版本）、TSC（Technical Steering Committee）、WG（Working Group，工作组）、P0/P1/P2/P3（用例与缺陷优先级，定义见框架§2、§9.1）

**核心原则：原子性，可重复性，可追溯性，完整性，独立性**

**检查项为规范条款**：本Checklist只约定"检查什么、依据什么规则"，具体准入门禁数值见框架§8，测试目标、场景与内容以测试方案/专项测试计划为准。

---

## 一、特性需求转测验收Checklist（TRR）

> 在特性开发完成后、进入FIT前执行
> 决策人：特性工作组Maintainer
> 执行人：特性工作组测试负责人
> 争议仲裁：TRR争议由集成测试工作组仲裁

| 分类 | 要求 | 检查项 | 规则描述 | 检查结果 | 备注 |
|------|------|--------|---------|---------|------|
| 代码与构建 | 必须 | 代码合入 | 【规则】特性相关代码已合入主干，版本标识（tag/commit ID）可追溯 | ☐ |  |
| | 必须 | 制品构建 | 【规则】测试所需制品已构建并推送至镜像仓库，制品清单与被测版本一致 | ☐ |  |
| | 必须 | 模块级UT | 【规则】模块级UT全部通过，以模块仓库流水线/日构建结果为准 | ☐ |  |
| | 必须 | UT覆盖率 | 【规则】满足框架§8.4覆盖率门禁，以模块仓库流水线要求为准 | ☐ |  |
| | 必须 | 可部署与冒烟 | 【规则】制品可部署且冒烟用例全部通过，以自动化执行结果为准 | ☐ |  |
| 需求与测试设计 | 必须 | 需求基线 | 【规则】特性提案/设计已通过TSC评审，需求基线冻结 | ☐ |  |
| | 必须 | 测试方案评审 | 【规则】测试方案按模板编写并评审通过，PR合入`openan-itest`仓库`docs/plans/<version>/` | ☐ |  |
| | 必须 | 用例规范 | 【规则】用例编号、命名、标签符合框架§6.1、§6.4规范 | ☐ |  |
| | 必须 | 用例自动化 | 【规则】P0/P1用例100%自动化且可重复执行；无法自动化的用例须声明原因并提供自验结果 | ☐ |  |
| | 必须 | 用例质量 | 【规则】用例满足框架§6.3编写要求（明确断言、禁止log-only、清理动作完整、禁止sleep与顺序依赖）；外部依赖相关用例的确定性要求以测试方案为准 | ☐ |  |
| 环境与数据 | 必须 | 环境可用性 | 【规则】测试环境可用性已由集成测试工作组确认 | ☐ |  |
| | 必须 | 数据与依赖就绪 | 【规则】测试方案声明的测试数据、账号权限与外部依赖就绪；外部依赖可按测试方案以桩/mock替代 | ☐ |  |
| 测试执行 | 必须 | 执行与通过率 | 【规则】满足框架§8.1 TRR准入门禁（用例执行率与各优先级通过率），以自动化执行结果为准 | ☐ |  |
| | 必须 | 失败用例处理 | 【规则】失败用例均归档issue并标注`skip-temporarily`，符合框架§6.4 | ☐ |  |
| | 必须 | 性能基线 | 【规则】关键接口性能不低于上一版本基线，基线以专项测试计划为准 | ☐ |  |
| | 必须 | 现场保留 | 【规则】失败用例现场（trace/log/截图等）保留完整，满足框架§6.3 | ☐ |  |
| 文档与归档 | 必须 | 方案与用例归档 | 【规则】测试方案与用例表合入`openan-itest`仓库`docs/plans/<version>/`，符合框架§11.3 | ☐ |  |
| | 必须 | 测试代码归档 | 【规则】自动化用例合入`openan-itest`仓库`e2e/<feature>/`，新增环境变量同步`.env.template`与README，符合框架§6.6 | ☐ |  |

**TRR决策：**
- [ ] 通过，进入FIT
- [ ] 有条件通过（遗留问题清单：______；issue链接：______；风险接受人：______；最迟关闭版本：______）
- [ ] 不通过，退回开发

**评审记录：** 评审日期______；参会人______；签核人______；证据链接（测试报告/pipeline/Allure）______

## 二、版本发布测试Checklist

> 在RC版本发布前、SIT执行期间和发布决策时使用，按RC准入→测试执行→发布决策的gate顺序执行
> 决策人：TSC/Release Manager
> 执行人：集成测试工作组
> 争议仲裁：发布争议提交TSC

| 分类 | 要求 | 检查项 | 规则描述 | 检查结果 | 备注 |
|------|------|--------|---------|---------|------|
| 测试环境 | 必须 | 环境基线 | 【规则】测试环境配置与生产基线核对一致，覆盖范围以发布测试计划为准 | ☐ |  |
| | 必须 | 环境核验 | 【规则】集成测试工作组已完成环境可用性核验 | ☐ |  |
| | 必须 | 依赖服务 | 【规则】发布测试计划定义的依赖服务全部可达 | ☐ |  |
| 版本构建与部署 | 必须 | RC版本 | 【规则】RC版本号、tag、changelog完整，符合版本管理规范 | ☐ |  |
| | 必须 | 镜像构建 | 【规则】全部组件镜像已构建并推送至镜像仓库 | ☐ |  |
| | 必须 | 制品完整性 | 【规则】发布物完整（SBOM、镜像签名、License清单），以流水线门禁与发布物清单为准 | ☐ |  |
| | 必须 | 部署形态 | 【规则】发布测试计划定义的受支持部署形态安装验证通过；范围外形态已显式声明排除 | ☐ |  |
| | 必须 | 升级与回滚 | 【规则】从上一版本的升级与回滚路径验证通过，升级操作符合部署契约 | ☐ |  |
| FIT全量回归 | 必须 | 全量执行 | 【规则】满足框架§8.2 FIT准出门禁（执行率、通过率、失败用例处理），以自动化执行结果为准 | ☐ |  |
| | 必须 | 新增特性覆盖 | 【规则】本版本新增特性FIT全部执行，准出标准同框架§8.2 | ☐ |  |
| SIT | 必须 | 组合场景 | 【规则】满足框架§8.3 SIT准出门禁（通过率、无跳过），场景范围以发布测试计划为准 | ☐ |  |
| | 必须 | 异常场景 | 【规则】异常与降级场景按测试方案执行通过，故障恢复后状态一致 | ☐ |  |
| 专项测试 | 必须 | 测试范围 | 【规则】专项测试类型与范围按框架§10及专项测试计划定义执行，准出标准以专项测试计划为准 | ☐ |  |
| | 必须 | 性能基线 | 【规则】关键接口性能达基线且不低于上一版本，基线以专项测试计划为准 | ☐ |  |
| | 必须 | 长稳与可靠性 | 【规则】长稳时长与判定阈值以专项测试计划为准，执行通过 | ☐ |  |
| | 必须 | 安全 | 【规则】安全扫描与安全特性验证通过，漏洞准出满足框架§8.3发布要求 | ☐ |  |
| | 必须 | 兼容性 | 【规则】兼容性矩阵按专项测试计划定义执行通过 | ☐ |  |
| 缺陷管理 | 必须 | 缺陷准出 | 【规则】满足框架§9缺陷管理要求：P0全部关闭、P1关闭或有明确规避方案，处理时限符合§9.1 | ☐ |  |
| | 必须 | 回归验证 | 【规则】每个修复均有对应回归用例并随修复PR执行通过，符合框架§9.2、§9.3 | ☐ |  |
| 覆盖率与追溯 | 必须 | 需求追溯 | 【规则】已批准需求100%有对应用例且已执行 | ☐ |  |
| | 必须 | 覆盖率 | 【规则】满足框架§8.4覆盖率门禁 | ☐ |  |
| 文档与发布物 | 必须 | 测试报告 | 【规则】测试报告按模板编写，经集成测试工作组评审通过并归档至`docs/reports/<version>/`，符合框架§11.3 | ☐ |  |
| | 必须 | 发布文档 | 【规则】Release Note与安装文档与当前版本一致，已知问题与规避方案完整 | ☐ |  |
| | 建议 | 体验环境 | 【规则】对外体验/演示环境冒烟通过（以发布范围声明为准） | ☐ |  |
| 发布决策 | 必须 | 质量数据汇总 | 【规则】各WG质量度量数据已汇总（用例执行/通过率、缺陷、自动化率、覆盖率等），以各WG测试报告为准 | ☐ |  |
| | 必须 | 遗留风险评估 | 【规则】遗留缺陷风险评估完成并记录，含规避方案、风险接受人与最迟修复版本 | ☐ |  |
| | 必须 | TSC评审 | 【规则】完成Go/No-Go发布决策评审 | ☐ |  |

**发布决策：**
- [ ] Go，正式发布
- [ ] No-Go，修复后重新评估（原因：______；重新评估范围：______）
- [ ] 有条件发布（遗留问题清单：______；风险接受人：______；最迟修复版本：______）

**评审记录：** 评审日期______；参会人______；签核人______；证据链接（测试报告/pipeline/Allure）______
