OpenAN Test Checklist

Version: v0.1
Based on: OpenAN Integration Testing Process and Framework v0.1
Maintained by: OpenAN Integration Testing Working Group
Applicable to: feature handover acceptance (TRR), release testing
Terminology: FIT (Feature Integration Test), SIT (System Integration Test), TRR (Test Readiness Review), RC (Release Candidate), TSC (Technical Steering Committee), WG (Working Group), P0/P1/P2/P3 (case and defect priorities, defined in Framework §2 and §9.1)

Core principles: atomicity, repeatability, traceability, completeness, independence

Check items are normative clauses: this checklist only defines "what to check and by which rule". Specific entry gate values are defined in Framework §8; test targets, scenarios, and content are defined in test plans / specialized test plans.

1. Feature Handover Acceptance Checklist (TRR)

Executed after feature development is complete and before entering FIT.
Decision maker: Feature WG Maintainer
Executor: Feature WG test owner
Dispute arbitration: TRR disputes are arbitrated by the Integration Testing WG.

2. Release Testing Checklist

Used before RC release, during SIT execution, and at the release decision point, executed in gate order: RC entry → test execution → release decision.
Decision maker: TSC / Release Manager
Executor: Integration Testing WG
Dispute arbitration: release disputes are escalated to the TSC.

CategoryRequirementCheck ItemRuleResultNotes
Test EnvironmentRequiredEnvironment baselineRule: Test environment configuration is verified consistent with the production baseline; coverage scope follows the release test plan☐
RequiredEnvironment verificationRule: The Integration Testing WG has completed environment availability verification☐
RequiredDependent servicesRule: All dependent services defined in the release test plan are reachable☐
Version Build & DeploymentRequiredRC versionRule: RC version number, tag, and changelog are complete, complying with version management conventions☐
RequiredImage buildRule: All component images have been built and pushed to the image registry☐
RequiredArtifact integrityRule: Release artifacts are complete (SBOM, image signatures, License inventory), based on pipeline gates and the release artifact list☐
RequiredDeployment modesRule: Installation verification passes for the supported deployment modes defined in the release test plan; out-of-scope modes are explicitly excluded☐
RequiredUpgrade & rollbackRule: Upgrade and rollback paths from the previous version pass verification; upgrade operations comply with the deployment contract☐
FIT Full RegressionRequiredFull executionRule: Meets the Framework §8.2 FIT exit gate (execution rate, pass rate, failed case handling), based on automated execution results☐
RequiredNew feature coverageRule: FIT for all new features in this version has been executed; exit criteria follow Framework §8.2☐
SITRequiredCombined scenariosRule: Meets the Framework §8.3 SIT exit gate (pass rate, no skips); scenario scope follows the release test plan☐
RequiredException scenariosRule: Exception and degradation scenarios pass per the test plan; state is consistent after fault recovery☐
Specialized TestingRequiredTest scopeRule: Specialized test types and scope are executed per Framework §10 and the specialized test plans; exit criteria follow the specialized test plans☐
RequiredPerformance baselineRule: Key interface performance meets the baseline and is not lower than the previous version; baselines are defined in the specialized test plan☐
RequiredStability & reliabilityRule: Stability test duration and pass thresholds follow the specialized test plan; execution passes☐
RequiredSecurityRule: Security scanning and security feature verification pass; vulnerability exit meets the Framework §8.3 release requirements☐
RequiredCompatibilityRule: The compatibility matrix passes per the specialized test plan definition☐
Defect ManagementRequiredDefect exitRule: Meets Framework §9 defect management requirements: all P0 defects closed, P1 closed or with documented workarounds; handling timelines comply with §9.1☐
RequiredRegression verificationRule: Every fix has a corresponding regression case that passes with the fix PR, per Framework §9.2 and §9.3☐
Coverage & TraceabilityRequiredRequirement traceabilityRule: 100% of approved requirements have corresponding executed cases☐
RequiredCoverageRule: Meets the Framework §8.4 coverage gate☐
Documentation & Release ArtifactsRequiredTest reportRule: The test report is written per template, reviewed and approved by the Integration Testing WG, and archived under docs/reports/<version>/, per Framework §11.3☐
RequiredRelease documentsRule: Release notes and installation documents match the current version; known issues and workarounds are complete☐
RecommendedExperience environmentRule: Smoke tests pass on the external experience/demo environment (per the declared release scope)☐
Release DecisionRequiredQuality data aggregationRule: Quality metrics from all WGs are aggregated (case execution/pass rates, defects, automation rate, coverage), based on each WG's test reports☐
RequiredResidual risk assessmentRule: Residual defect risk assessment is complete and recorded, including workarounds, risk acceptors, and the latest fix version☐
RequiredTSC reviewRule: The Go/No-Go release decision review is completed☐

3. Notes on the Test Environment as an Acceptance Item

StageEnvironment accepted?Rationale
TRR (feature handover)❌ NoThe environment is provided and guaranteed by the Integration Testing WG; the feature WG only needs to confirm "environment available". The environment itself is not an acceptance criterion (see Chapter 1, "Environment & Data" category)
Release testing✅ YesBefore release, it must be confirmed that the test environment has passed all tests and its configuration matches production (see Chapter 2, "Test Environment" category)
