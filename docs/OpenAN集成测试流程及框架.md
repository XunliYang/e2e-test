## 1. 目的与范围

**1.1 目的**

- 规范 OpenAN 社区集成测试的定义、流程与质量门禁，确保各工作组与社区伙伴在同一套规则下交付可集成的代码；
- 降低发布前的集成风险，避免"各模块单元测试全部通过、集成后却失败"的情况；
- 为贡献者提供"如何为 OpenAN 编写集成测试"的明确指引。

**1.2 范围**

- 适用于 OpenAN 社区全部代码仓库及对应的集成测试仓库；
- 适用于社区版本发布前的全部集成测试活动，包括特性集成测试（FIT）、系统级集成测试（SIT）与专项测试；
- 不替代单元测试（UT）与静态代码分析；单元测试由各工作组在模块仓库内自行管理。

**1.3 读者**

- 贡献者、工作组测试负责人、评审人、集成测试工作组成员、Maintainer、版本发布管理人员。

## 2. 术语

| 术语 | 定义 |
| --- | --- |
| 特性（Feature） | OpenAN 社区的功能单元，按工作组组织，对应一个或多个代码仓库。 |
| 工作组（WG） | OpenAN 社区按职责组织的协作单元，如集成测试工作组、Infra 工作组。 |
| 特性集成测试（FIT） | 在单一特性内，验证多个模块/服务在真实环境中正确集成并满足需求。 |
| 系统级集成测试（SIT） | 在 OpenAN 发行版层面，验证多特性在典型场景下的稳定性、可用性与兼容性。 |
| 转测就绪评审（TRR） | 特性开发完成后、进入 FIT 前的验收检查点；准入标准为 P0/P1 用例通过率 100%。 |
| 质量门禁（Quality Gate） | 一组必须全部通过的自动化检查，包括测试通过率、覆盖率、License、敏感信息等。 |
| 发布候选版本（RC） | 由版本发布管理定期发布、供社区伙伴试用与验证的联调候选版本。 |
| 长稳测试 | 7×24 小时连续运行，验证系统在长时间负载下的稳定性。 |
| 集成测试工作组 | 负责整体质量保障与测试体系维护的工作组。 |
| Infra 工作组 | 负责 CI 工程与门禁流水线维护的工作组。 |

## 3. 角色与职责

| 角色 | 职责 |
| --- | --- |
| 贡献者（Contributor） | 提交代码及配套集成测试用例；确保用例可重复、可自动执行；响应评审意见。 |
| 评审人（Reviewer） | 评审测试方案、测试代码与测试报告；检查是否符合本规范；确认质量数据。 |
| 工作组测试负责人（WG Test Owner） | 每个工作组一名；统筹本工作组的测试方案与进度，向集成测试工作组汇报；不要求亲自执行测试。 |
| 集成测试工作组 | 维护本规范、模板与测试用例；提供自动化用例模板及生成/执行技能；组织测试方案与报告评审；执行 SIT 与专项测试；汇总质量数据。 |
| Infra 工作组 | 维护 CI 流水线、门禁检查与日构建；确保测试环境可用、可复用。 |
| Maintainer | 对合入的代码及配套测试承担最终责任；检查门禁结果；批准特性 TRR。 |
| TSC | 确定 RC 发布节奏与发布评审；决策 Go / No-Go。 |

**3.1 测试负责人要求**

- 任期至少覆盖一个完整版本周期；
- 可来自本工作组或集成测试工作组；
- 须对本工作组内测试工作项有全局了解。

## 4. 总体集成测试流程

### 4.1 流程总览

```mermaid
flowchart LR
    S1["1. 需求/设计<br/>（需求基线）"] --> S2["2. 测试设计<br/>（方案与用例）"] --> S3["3. TRR 门禁<br/>（P0/P1 通过）"] --> S4["4. 测试执行<br/>（FIT / SIT）"] --> S5["5. 评审<br/>（异步评审）"] --> S6["6. 发布<br/>（发布门禁）"]
```

### 4.2 阶段说明

**阶段 1：需求与设计**

- 特性提案通过 TSC 评审后方可开始测试设计；
- 产出：特性测试方案（含 FIT 范围、SIT 范围、所需环境、数据与进度安排）。

**阶段 2：测试设计**

- 按模板编写测试方案，测试用例以 CSV/表格形式附上；
- 用例必须标注优先级（P0/P1/P2）、环境与依赖；
- 测试方案以 PR 提交至 `openan-itest` 仓库对应版本目录，由集成测试工作组通过 PR 评审，评审通过后合入。

**阶段 3：转测就绪评审（TRR）**

- 触发条件：特性代码开发完成、模块级 UT/DT 全部通过、镜像已构建；
- 准入标准：自动化 FIT **P0/P1 用例通过率 100%**；P2 用例通过率 ≥ 80%；
- 决策人：特性工作组 Maintainer；
- 评审通过后，特性正式进入"特性集成测试"阶段。

**阶段 4：测试执行**

- 特性集成测试（FIT）：在真实环境中执行该特性的全部 FIT 用例；
- 系统级集成测试（SIT）：由集成测试工作组在 RC 版本上执行，覆盖多特性组合场景；
- 执行结果必须自动采集：用例通过率、失败用例清单、trace/日志/截图、性能指标。

**阶段 5：报告评审**

- 特性工作组测试负责人按模板编写特性测试报告；
- 集成测试工作组组织评审会（线上/线下），重点关注：用例覆盖目标是否达成、遗留问题是否有规避方案、性能是否达基线。

**阶段 6：归档与发布**

- 测试方案、测试报告与测试代码全部归档至 `openan-itest` 仓库；
- 版本发布管理人员依据 SIT 结果与遗留问题清单，决定版本是否进入正式发布。

### 4.3 测试时间线（版本周期）

> 各阶段具体日期以版本 Release Plan 为准（参考 [OpenAN 26.12 Release Plan](https://lf-networking.atlassian.net/wiki/spaces/OpenAN/pages/1187905545/OpenAN+26.12)）；交付物模板位于 `openan-itest` 仓库 `docs/templates/` 目录。

#### 4.3.1 转测（M4：测试设计与评审）

**前置条件**：M4 特性开发冻结窗口开启，特性需求基线冻结。

**操作流程：**

1. 特性工作组在 `openan-itest` 仓库提交转测 issue（关联需求与特性范围）；
2. 以 PR 提交按[测试方案模板](https://github.com/project-openan/openan-itest/blob/main/docs/templates/test-plan-template.md)编写的测试方案与按[测试用例表模板](https://github.com/project-openan/openan-itest/blob/main/docs/templates/testcases-template.csv)填写的用例表，并合入 FIT 自动化测试用例；
3. 集成测试工作组组织方案、用例与自动化代码评审；
4. 评审通过后完成转测。

**特性工作组**：交付测试方案、测试用例表、FIT 自动化测试用例（合入 `e2e/<feature>/`）。
**集成测试工作组**：组织评审，交付评审意见与 TRR 结论。
**验收内容**：测试方案评审通过；用例符合规范（P0/P1 100% 自动化、需求链接齐备）；自动化用例独立可重复执行。

#### 4.3.2 RC-0（全量测试与需求验收）

**前置条件**：特性开发完成、全量转测完成，RC-0 版本镜像包构建完成。

**操作流程：**

1. 特性工作组测试责任人执行 FIT 全量自测，输出自测报告；
2. 集成测试工作组部署 RC-0 镜像包并完成部署验证；
3. 执行全量 FIT/SIT 回归，启动专项测试（性能、7×24h 长稳、安全、兼容性、A2A-T 协议等）；
4. 依据测试报告核对覆盖率与通过率要求，完成需求验收；
5. 特性工作组修复 P0/P1 缺陷或提供规避方案，集成测试工作组输出 RC-0 测试报告。

**特性工作组**：交付 FIT 自测报告、缺陷闭环记录。
**集成测试工作组**：执行回归与专项测试，交付 RC-0 测试报告与需求验收结论。
**验收内容**：通过率满足框架 §8.2（P0/P1=100%、总体≥95%）；覆盖率满足框架 §8.4（需求覆盖率 100%、API 覆盖率≥80%）；缺陷处理符合框架 §9.1 时限；RC-0 测试报告发布。

#### 4.3.3 RC-1（发布前测试）

**前置条件**：RC-0 问题修复完成，RC-1 版本镜像包构建完成。

**操作流程：**

1. 集成测试工作组部署 RC-1 镜像包；
2. 执行全量 FIT/SIT 回归与专项测试收尾（长稳结论等）；
3. 输出 RC-1 测试报告并汇总质量数据，作为发布决策输入；
4. TSC 发布评审（Go/No-Go）。

**特性工作组**：遗留缺陷闭环与风险接受，交付遗留问题清单。
**集成测试工作组**：交付 RC-1 测试报告与质量数据汇总，给出发布建议。
**验收内容**：满足框架 §8.3 发布准入（SIT 通过率 100% 无跳过、长稳无 P0/P1 故障、安装/升级/回滚通过、P0 缺陷全部关闭）；质量数据汇总完成。

## 5. 测试分层与范围

### 5.1 分层模型

| 层级 | 执行人 | 环境 | 关注点 | 用例形态 |
| --- | --- | --- | --- | --- |
| 单元测试（UT） | 开发者 | IDE / Mock | 单个函数/类的正确性 | 模块仓库内 `<pkg>_test.go` / `test_*.py` |
| 开发者自测（DT） | 开发者 | 本地集群 | 模块对外接口契约 | 模块仓库内冒烟 e2e 用例 |
| **特性集成测试（FIT）** | 特性工作组 | **真实环境** | 特性内多个模块/服务的集成正确性 | `openan-itest` 仓库特性目录 |
| **系统级集成测试（SIT）** | 集成测试工作组 | **真实环境 + 典型场景** | 发行版整体稳定性、可用性、兼容性 | `openan-itest` 仓库 `system-integration/` |
| 专项测试 | 集成测试工作组 | 按专项而定 | 性能、安全、兼容性、长稳、文档、一致性 | 专项目录 |

### 5.2 集成测试边界

**纳入集成测试（FIT/SIT/专项测试）**

- 跨模块 API 调用、跨服务数据流、事件触发链；
- 安装/升级/回滚路径；
- 多特性组合使用（如 registry + orchestrate + execute）；
- 在真实 Kubernetes 集群或虚拟机上验证终端用户关键路径；
- 专项测试：性能、压力、长稳、可靠性、安全、兼容性、A2A-T 协议等（由集成测试工作组执行，类别见第 10 章）。

**不纳入集成测试（不在集成层做以下事情）**

- 单个函数的边界条件（应在 UT 覆盖）；
- 纯 UI 布局与样式（属前端手工/UI 自动化，本规范不覆盖）。

## 6. 测试用例规范

### 6.1 用例编号与命名

- 用例编号格式：`FIT-<feature>-<topic>-<number>`（如 `FIT-orchestration-workflow-001`）；SIT 用例为 `SIT-<scenario>-<number>`；
- 用例描述使用英文，格式：`<case-id> - Case Description`；
- **测试文件命名**：`test_<topic>.py`，topic 为特性下的功能场景，小写下划线分隔（如 `test_workflow.py`、`test_agent.py`）；
- **测试函数命名**：`test_<action>_<expected_result>`，明确表达动作与预期结果（如 `test_create_workflow_success`、`test_delete_agent_not_found`）；
- **可选类分组**：同一 topic 用例较多时可用 `Test<Topic>API` 类分组（如 `TestWorkflowAPI`），类内方法仍以 `test_` 开头；
- **Playwright 测试文件**：`test-<scenario>.spec.ts`。

### 6.2 目录结构

```
openan-itest/
├── e2e/                              # 后端集成测试（pytest）
│   ├── framework/                    # 共享能力：K8s client、env 加载、工具函数
│   ├── <feature>/                    # 每特性一个目录
│   │   ├── test_<feature>_api.py
│   │   ├── test_<topic>.py
│   │   ├── system-integration/       # 该特性的系统级集成用例
│   │   │   └── test_<scenario>.py
│   │   └── utils/  static/
│   └── .env.template
├── e2e-frontend/                     # 前端 UI 自动化（可选）
├── testcases/functional/integration/ # pytest（遗留栈，按需保留）
├── docs/                             # 测试方案与报告归档
│   ├── plans/                        # 按版本归档测试方案
│   └── reports/                      # 按版本归档测试报告
└── README.md
```

### 6.3 用例编写要求

- 每条用例必须包含：前置条件、步骤、断言、清理动作；
- 断言必须明确；禁止只记日志不断言；
- 用例必须独立可重复；禁止依赖其他用例的执行顺序（确需顺序时用 `Ordered` / `test.describe.serial` 显式声明）；
- 多条强相关用例可合并为一个测试函数，减少重复的上下文创建；
- 禁止用 `sleep` 做同步；使用框架提供的等待/重试机制（Playwright auto-wait、`eventually` 等）；
- 失败时保留现场：trace、截图、相关 Pod 日志、K8s 事件。

### 6.4 标签

每条用例必须至少携带以下标签维度：

| 维度 | 示例 | 说明 |
| --- | --- | --- |
| feature | `registry-center`、`orchestration-center` | 模块标识 |
| environment | `with-workload-cluster`、`online`、`offline` | CI 环境过滤 |
| components | `registry-center`、`openan-portal` | 所需组件 |
| priority | `P0`、`P1`、`P2` | 用例优先级 |
| skip | `skip-temporarily` | 临时跳过；必须引用 issue 链接 |
| **execution** | `smoke`、`full`、`slow` | PR CI 跑 `smoke`，Daily 跑 `full` |

### 6.5 数据准备与清理

- 测试数据通过 fixture 提供；按需选择 function/class/module/session 级别；
- 每条用例必须在 teardown 中清理：删除创建的命名空间、CR、Pod、PV、配置；
- 严格禁止用例间共享可变状态；session 级 fixture 仅用于只读配置（如 LLM 配置、登录态）。

### 6.6 配置与密钥

- 所有外部依赖（集群地址、凭据、SSH、镜像仓库）通过环境变量注入；
- 仓库内仅保留 `.env.template`；**严禁提交 `.env` 或任何真实凭据**；
- 代码评审时检查是否硬编码 IP/密码/token；发现即拒绝合入。

## 7. 自动化框架与工具链建议

### 7.1 推荐技术栈

| 用途 | 首选 | 备选 | 说明 |
| --- | --- | --- | --- |
| 后端集成测试 | pytest（Python） | - | 与 OpenAN 主代码同语言，可复用客户端与类型 |
| 前端 UI 测试 | Playwright（TypeScript） | pytest + Playwright（Python） | Playwright auto-wait + Trace 能力成熟 |
| K8s 资源管理 | client-go / kubernetes-client python | - | 框架内已封装 |
| 集群生命周期 | kind / k3s（本地）、社区实验室（真实集群） | - | FIT 在真实集群执行 |
| 测试报告 | JUnit XML + Allure | - | CI 汇聚与展示 |

### 7.2 CI 触发策略

- **PR 触发**：仅执行受影响特性目录下的 FIT 用例，标签过滤 `--label-filter="!<skip-temporarily>"`；
- **日构建触发**：全量 FIT + 冒烟 SIT；
- **RC 版本触发**：全量 FIT + 全量 SIT + 启动长稳测试；
- **预发布触发**：在 RC 上重跑全部 P0/P1 + 全部 SIT，作为发布评审输入。

### 7.3 门禁流水线

Infra 工作组维护的 PR 门禁流水线至少包含：

1. License / DCO 检查；
2. 代码风格与静态分析；
3. 接口变更检查（兼容性）；
4. 敏感信息扫描（密钥、内网 IP）；
5. 受影响特性目录下的冒烟 FIT 用例。

通过门禁后，CI 方可合入并发布日构建。

## 8. 准入与准出标准（质量门禁）

### 8.1 TRR（FIT 准入）

- P0 用例通过率 = 100%；
- P1 用例通过率 = 100%；
- P2 用例通过率 ≥ 80%；
- 模块级 UT 覆盖率不下降（与上一版本相比）；
- 镜像可构建且可部署。

### 8.2 FIT 准出

- FIT 用例总体通过率 ≥ 95%；
- 失败用例均归档 issue 并标注 `skip-temporarily`；
- 性能不低于上一版本基线（关键接口 P99 时延、资源占用）；
- 测试报告经集成测试工作组评审通过。

### 8.3 SIT 准出 / 发布准入

- SIT 用例总体通过率 = 100%（不允许跳过）；
- RC 上 7×24 小时连续长稳运行无 P0/P1 故障；
- 安装、升级、回滚路径全部通过；
- 无未关闭 P0 缺陷；P1 缺陷有明确规避方案与修复计划；
- 兼容性矩阵（OS × 硬件 × 依赖版本）通过。

### 8.4 覆盖率要求

- 模块仓库 UT 行覆盖率 ≥ 70%（核心模块 ≥ 80%）；
- 集成测试 API 覆盖率 ≥ 80%（按 OpenAPI paths 统计）。

## 9. 缺陷管理与回归

### 9.1 缺陷分级

| 级别 | 定义 | 修复时限 |
| --- | --- | --- |
| P0 | 阻断级：安装失败、数据丢失、核心功能不可用 | 必须 24 小时内响应；必须在本版本修复 |
| P1 | 严重级：主要功能受损，但有临时规避方案 | 3 个工作日内修复 |
| P2 | 一般级：次要功能问题 | 下一版本修复 |
| P3 | 轻微级：UI、文案、体验类 | 按需排期 |

### 9.2 缺陷流程

1. 失败用例自动创建 issue，并附 trace/日志/截图/集群信息；
2. 缺陷责任由工作组测试负责人 + Maintainer 确认；
3. 修复后必须补充回归用例并重跑 FIT；
4. RC 发布前，全部 P0/P1 缺陷必须关闭或有明确规避方案。

### 9.3 回归策略

- 每个修复 PR 必须重跑该特性的全部 FIT 用例；
- 每个 RC 版本必须重跑全部 P0/P1 用例；
- 正式发布前必须完成一次全量回归。

## 11. 贡献指南

### 11.1 提交集成测试用例

1. **签署 CLA**（首次贡献前必须完成）；
2. **Fork 与分支**：从 `openan-itest` 的 `main` 创建 `<feature>/<your-name>-<short-desc>`；
3. **本地开发**：遵循本规范第 6、7 章；在真实或临时集群上完成本地验证；
4. **自测**：`pytest tests/api/python/<feature> -m "not slow"` 通过；
5. **提交 PR**：PR 描述包含：特性名称、用例数量、本地执行结果、是否需要新增环境变量；
6. **CI 检查**：通过门禁（License、静态分析、冒烟 FIT）；
7. **代码评审**：工作组评审人 + 集成测试工作组双重评审；
8. **合入**：Maintainer 批准并合入；用例进入日构建。

### 11.2 评审标准

- 用例符合本规范（命名、标签、断言、清理）；
- 包含必要的反向/异常用例；
- 无硬编码、sleep、隐式顺序依赖；
- 失败现场信息充分（trace/日志/截图）；
- 新增环境变量已加入 `.env.template` 并在 README 文档化。

### 11.3 测试方案与报告

- 测试方案：使用模板，附用例 CSV，以 PR 提交至 `openan-itest` 仓库 `docs/plans/<version>/` 目录；
- 测试报告：使用模板，含执行数据、遗留问题、性能数据，以 PR 提交至 `openan-itest` 仓库 `docs/reports/<version>/` 目录；
- 两者均经集成测试工作组评审后归档。
