# 测试包编排设计指导（README 先行）

## 1. 定位

生成测试代码**之前**，先为目标仓库的测试包产出**架构规划与执行方案**（即该仓 `tests/README.md`），经用户确认后作为代码编排与生成的唯一依据。

**输入**：评审用例 CSV（openan 12 列）+ 编排输入（§3）。
**输出**：目标仓 `tests/README.md`（编排设计）；经用户确认后才进入代码生成。

## 2. 编排设计做什么

把用例表的「文本步骤」落成「可执行编排」，逐项回答：

| 编排问题 | 落点（README 章节 / 代码） |
|----------|---------------------------|
| 每条用例写到哪个文件 | 目录结构 + 用例覆盖映射 |
| 前置条件如何准备 | fixtures / conftest.py / setup.bash / `@BeforeEach` |
| 依赖哪些环境与凭据 | 环境变量契约（`.env.template`） |
| 跨组件依赖如何启动 | docker compose 服务拓扑（component_deps 列展开） |
| 步骤用什么 API 编排 | 目标仓既有 client / SDK 复用清单 |
| 协议用例怎么编排 | A2A-T SDK（python/java）或 REST 客户端；原语来自 protocol_primitive 列 |
| 预期如何断言 | 断言风格按 profile（assert / AssertJ / expect / bats-assert） |
| 怎么跑起来 | 运行方式（pytest / mvn / vitest / bats 命令、标记过滤、超时） |

## 3. 编排输入清单（生成 README 前必须齐备）

| 编排输入 | 要回答的问题 | 典型来源 |
|----------|--------------|----------|
| 目标仓库 | owner/repo 与本地路径；主语言；既有测试目录约定 | 用户、仓库结构 |
| 包定位与范围 | unit / integration / e2e 分层边界；本批用例落在哪层 | 用户、用例 precondition |
| 部署与启动方式 | 被测服务怎么起（docker compose？`uv run`？已有服务地址？） | 用户、目标仓 README/docs |
| 环境拓扑 | 单组件 or 多组件（component_deps 列）；compose 文件位置、服务名、端口 | CSV、目标仓 compose 文件 |
| 环境变量契约 | 服务地址、token、测试数据位置；哪些可缺省 | 目标仓 `.env.template`、docs |
| 凭据与权限 | 注册/鉴权所需 token 从哪来（Authorization-T 用例必备） | 用户、目标仓配置 |
| 套件生命周期 | 启动/清理顺序（compose up/down、临时目录隔离） | profile 文件、目标仓既有测试 |
| 复用清单 | 目标仓既有测试 helpers / fixtures / SDK 客户端 | 读目标仓既有测试代码 |
| 运行与过滤方式 | 按标记/case_id 过滤的命令、超时建议 | profile 文件 |

**STOP**：以上任一项无法从用户输入、CSV 或目标仓代码中确定时，逐项列出缺失项并停止，禁止编造。

## 4. README 必备章节（对齐 templates/test-package-readme.example.md）

1. 测试范围（用例编号 ↔ 验证内容 ↔ 状态映射表）
2. 目录结构（按 profile 约定）
3. fixtures / 测试数据
4. 环境变量契约（`.env.template` 片段 + 变量表）
5. 跨组件拓扑（component_deps 非 none 时：compose 服务清单与启动顺序）
6. 套件生命周期（setup/teardown）
7. 运行方式（含按 case_id / 标记过滤的命令）
8. 已知限制（可选：skip 条件、资源敏感场景）

## 5. 可执行性检查清单（README 评审口径）

- [ ] 每条用例的前置条件都有对应 fixture/setup 落点
- [ ] 每个 `见结果N` 都有对应断言实现方案（含 DFX 用例的日志/指标观测手段）
- [ ] 每个环境变量都有来源与缺省行为说明
- [ ] 协议用例（protocol_primitive ≠ none）明确所用 SDK 与样本数据来源
- [ ] 运行命令在目标仓根目录可直接执行
