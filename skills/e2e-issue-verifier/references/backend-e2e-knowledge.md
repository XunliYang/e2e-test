# 后端 E2E 排查领域知识库

本知识库作为 `e2e-issue-verifier` 的领域知识支撑，用于后端 pytest / Maven / bats 失败分析时校准真实命令执行路径、依赖安装阶段阻塞、服务编排状态和常见环境问题。

它不是流程文档；流程由 `SKILL.md` 负责。本文件只回答一件事：**遇到后端 E2E 失败时，应该如何基于 stdout/stderr、测试报告和服务/容器状态做更通用、更可执行的诊断。**

## 与 `SKILL.md` 的调用关系

### `SKILL.md` 负责什么

`SKILL.md` 负责：
- 识别前端 / 后端验证路径与语言 profile
- 生成最小验证命令
- 接管日志、trace、stdout/stderr、Issue 评论等证据
- 输出根因、修复状态、FixContext、交接建议
- 控制是否交给 `github-issue-fixer` 或 `github-issue-creator`

### 本知识库负责什么

本知识库负责：
- 解释本地 / SSH 远程测试环境的真实状态
- 约束分析时的证据优先级
- 定义依赖安装失败、环境阻塞、工具版本不匹配、服务/容器状态异常的通用判定规则
- 提供更稳定的后端诊断锚点
- 把“看起来像用例失败”的问题拆成可验证的结构性原因

### 使用方式

当 `SKILL.md` 分析后端失败时，必须主动参考本知识库，特别是：
- SSH 连接与远程目录执行（仅 bats 安装类场景）
- pytest collection error / fixture 失败 / 断言失败
- Maven 编译失败 / surefire 跳过 / `-Dtest` 过滤
- bats `--filter` / `setup`/`teardown` 污染
- `.env` 配置缺失或错误
- docker-compose 编排、服务健康检查、容器状态

如果本知识库能解释当前失败结构，则优先按本知识库的规则定位；如果不能解释，则回到 stdout / stderr / trace / 服务状态继续补证据，而不是直接扩大验证范围。

## 0. 通用诊断原则

当后端测试失败时，必须按以下顺序排查：

1. 先判断是否是 **连接问题**（仅远程场景）
   - SSH 不通
   - 认证失败
   - 端口不可达
   - 主机名 / IP 错误

2. 再判断是否是 **执行环境问题**
   - 目标目录不存在
   - `.env` 配置不完整
   - 依赖未安装（未 `uv sync` / Maven 依赖未解析 / bats 未安装）
   - 工具链版本不匹配（Python/JDK/Maven/Node/bats 版本与仓库要求不符）
   - 基础工具缺失

3. 再判断是否是 **收集/编译问题**
   - pytest collection error（import 失败、conftest 报错、语法错误）
   - Java 编译失败（方法 / 字段不存在、import 缺失、API 变更未同步）
   - bats 语法错误或未找到测试文件

4. 再判断是否是 **测试代码问题**
   - 断言过严
   - 断言对象选错（stdout / stderr / 日志文件）
   - 等待不足（轮询间隔、超时）
   - fixture/teardown 未清理，污染后续用例
   - 用例名或过滤表达式写错

5. 再判断是否是 **被测系统问题**
   - 服务启动失败、健康检查不通过
   - 容器退出（`docker compose ps` 显示 `Exit 1`）
   - API 返回 5xx、注册/发现逻辑错误

6. 最后才考虑 **时序 / flaky**
   - 服务最终一致性等待不足
   - 启动慢
   - 初始化收尾阶段未完成

在未排除前述结构性问题前，不得直接把失败归因为“环境太慢”或简单扩大 timeout。

## 1. 本地与远程执行环境特征

### 1.1 命令成功启动不等于验证已完成

- 命令能启动，只能说明工具链与目录基本可用。
- 不代表依赖已就绪。
- 不代表服务编排已完成。
- 不代表测试已经执行到目标用例（pytest 可能停在 collection 阶段，Maven 可能停在编译阶段）。

诊断时要区分：
- “能进入目录”
- “能启动测试进程”
- “通过收集/编译阶段”
- “能跑到目标用例并给出断言结果”

### 1.2 目录必须是真实工作目录

后端 e2e 通常要求在仓库根或 `tests/` 目录下执行测试命令。
如果目录不对，常见现象包括：
- 找不到 `pyproject.toml` / `pom.xml` / 测试文件
- pytest 报 `file or directory not found`
- Maven 报 `no tests to run`（过滤条件没匹配到）
- bats 报 `does not exist`

### 1.3 `.env` 是后端验证的重要前置条件

常见环境变量包括：
- 服务地址、端口（registry-center / orchestration-center 端点）
- token / 凭证
- 数据库或消息队列连接串
- `KUBECONFIG` 或 docker 相关配置（安装类场景）

若 `.env` 缺失或为空，可能会导致：
- 连接被拒（connection refused）
- 认证失败（401/403）
- 用例 setup 阶段即失败

## 2. pytest 失败诊断规则

### 2.1 collection error 优先级高于用例失败

如果 pytest 在进入具体用例之前就失败，通常是：
- import 错误（依赖未安装、循环 import）
- conftest.py 报错（fixture 定义错误、插件缺失）
- 测试文件语法错误

这种问题不应被误判成原始 e2e 用例失败。`pytest --collect-only -q` 可快速隔离收集问题。

### 2.2 fixture 与 teardown 是一类独立问题

如果失败现象是「单跑通过、串跑失败」或「前一个用例影响后一个用例」，优先考虑：
- fixture 作用域过大（session/module 级共享状态未重置）
- teardown 未执行或不彻底（注册的数据未注销、临时文件未清理、服务未重启）

这属于**测试代码缺陷**，不是被测系统问题。

### 2.3 stdout / stderr / 日志文件要分开看，也要合并看

被测服务与测试脚本的提示可能出现在：
- 命令 `stdout`
- 命令 `stderr`
- 服务自身日志文件（`.test-output/<timestamp>/` 下归档）

因此遇到“输出中找不到某个完成文案”时，要先判断：
- 断言是否只看了 pytest 捕获的输出
- 成功提示是否实际在服务日志里（`-s` 或 `--show-capture` 查看）
- 文案是否被升级或变更

### 2.4 断言失败不一定代表业务失败

如果只是不匹配某个固定字符串，通常优先考虑：
- 测试断言过严
- 输出文案变化
- 成功信号位置变化

只有在结合退出码、服务状态与后置检查都不成立时，才判定为被测系统失败。

## 3. Maven / JUnit5 失败诊断规则

### 3.1 编译失败优先级高于用例失败

如果 Maven 在 surefire 启动前就失败，通常是：
- 编译错误（方法 / 字段不存在、API 变更未同步）
- 依赖无法解析（私仓不可达、版本不存在）

这类问题属于**编译阻塞**，不是 e2e 用例业务失败。先看 `mvn compile` 或构建日志中的 `[ERROR]` 编译段。

### 3.2 `-Dtest` 过滤未命中是一类独立问题

现象是构建成功但 `no tests to run` / `Tests run: 0`：
- 类名或方法名拼写错误（注意 `*IT` 与 `*Test` 的 surefire/failsafe 区别）
- 未加 `-DfailIfNoTests=false` 之外的正确定位：先 `mvn test -Dtest=ClassName` 再细化到方法

### 3.3 WireMock / 模拟服务端口占用

集成测试常内嵌 WireMock 等模拟服务：
- 端口被上次未清理的进程占用 → 后续用例全部失败
- 属于环境问题或 teardown 不彻底，不是业务回归

## 4. bats / 安装部署场景知识

### 4.1 成功判定不应只依赖单一字符串

安装/初始化流程往往输出多阶段日志（参数解析、环境检查、节点信息、配置写入、收尾）。如果测试只断言固定字符串，就可能因为文案改写、输出流变化、版本间提示差异而误判。

更稳妥的判定通常应结合：
- exit code
- 关键阶段日志
- 后置状态检查（服务是否监听、配置是否生成、`docker compose ps` 是否健康）

### 4.2 setup / teardown 必须成对

bats 的 `setup`/`setup_file` 与 `teardown`/`teardown_file` 不配对时，典型现象是：
- 首个用例通过、后续用例失败（端口/目录/容器残留）
- 修复方向是补 teardown，不是放宽断言

### 4.3 关注“是否真的执行到终点”

有些失败表面上看像“初始化没有成功”，实际上只是：
- 命令已成功执行
- 核心动作已完成
- 但最后的 completion 文案没有命中

这时应优先检查结束态与 exit code，而不是只盯着某个字符串。

## 5. 服务 / 容器状态诊断规则

### 5.1 后置状态检查是关键证据

对于安装、初始化、升级、部署类用例，后续通常要检查：
- `docker compose ps` 各服务是否 `running` / `healthy`
- 健康检查端点是否返回 200
- 关键进程是否监听预期端口
- 多组件编排时上游组件（如 registry-center）是否先于下游（orchestration-center）就绪

如果这些状态不成立，才更像真正的被测系统问题。

### 5.2 常见状态含义

- `running` / `healthy`：通常是正常态
- `starting` / `unhealthy`：启动中或健康检查未过（时序问题高发区）
- `exited (1)`：容器启动 / 配置问题
- `connection refused`：服务未监听（未启动或启动失败）
- 端口冲突：宿主机端口被占用（环境残留）

### 5.3 不要把编排状态问题误判为测试文案问题

如果日志断言失败，但 `docker compose ps` 显示服务异常，说明问题可能已超出测试本身。
如果日志断言失败，但后置状态全部正常，则更应怀疑测试断言不稳。

## 6. 文件 / 工具 / 命令缺失规则

### 6.1 `ModuleNotFoundError` / `cannot find symbol`

通常说明：
- 依赖未安装或版本不一致
- 代码引用了不存在的 API
- 重构后未同步调用方

这类问题属于**依赖/编译阻塞**，不是 e2e 用例业务失败。

### 6.2 `command not found`

通常说明：
- 目标机器缺少工具（uv / mvn / bats / docker）
- PATH 未配置
- 运行环境与预期不一致

### 6.3 `No such file or directory`

通常说明：
- 仓库路径错误
- 临时文件未生成
- 模板或配置文件缺失

### 6.4 `unrecognized arguments` / `Unknown lifecycle phase`

通常说明：
- 命令参数与当前工具版本不兼容
- CLI 版本和仓库期望版本不一致
- pytest 插件缺失（参数由插件提供时）

## 7. 后端最小验证命令诊断规则

### 7.1 最小验证应优先单用例 / 单文件 / 单标签

原则上优先使用：
- pytest：`pytest path/to/test_file.py::test_name` 或 `-k "关键字"`
- Maven：`mvn test -Dtest=ClassName#methodName`
- bats：`bats file.bats --filter "用例名"`

不要默认先跑全量。

### 7.2 命令位置与参数顺序要与工具版本兼容

不同版本对参数位置的要求可能不同（如 pytest 的 `-k` 要放在路径前，Maven 的 `-D` 系统属性要放在 goal 前）。
如果出现参数解析类错误，应优先考虑：命令顺序错误、CLI 版本不匹配。

### 7.3 只跑到收集/编译阶段不算完成最小验证

如果命令只完成了：
- 目录进入
- 依赖解析
- 收集/编译

但没有进入目标用例，则只能说明“前置环境基本可用”，不能算作“目标用例已验证”。

## 8. 后端失败分类与结论模板

### 8.1 推荐分类

- SSH / 网络失败（仅远程场景）
- 目录 / 权限失败
- `.env` 配置失败
- 工具链 / 版本失败
- 依赖安装失败
- 收集 / 编译失败
- 测试断言问题
- 被测系统问题
- 服务 / 容器状态异常
- 时序 / flaky

### 8.2 结论判断原则

- 如果命令未进入目标用例执行阶段：标记为“验证受阻”
- 如果进入了目标用例但断言失败：先判断是测试问题还是业务问题
- 如果后置服务/容器状态异常：更偏向被测系统问题
- 如果仅 completion 文案不命中，但 exit code 与后置状态都正常：更偏向测试断言问题

## 9. 与 `e2e-issue-verifier` 的配合方式

### 9.1 `SKILL.md` 应该先做什么

- 读取失败日志、trace、报告、Issue 评论
- 生成最小验证命令
- 判断属于前端还是后端、后端属于哪种语言 profile
- 收敛到最小用例 / 最小文件
- 输出根因、FixContext、修复状态建议

### 9.2 本知识库应当提供什么

- 为什么命令成功启动并不等于最小验证成功
- 为什么 collection / 编译失败要优先处理
- 为什么 completion 文案不能只看固定字符串
- 为什么服务/容器后置状态比单一日志更可靠
- 何时应判定为结构性问题而不是简单的等待问题

### 9.3 分工边界

- `SKILL.md` 负责流程、交接、验证、结论
- 本知识库负责后端 pytest / Maven / bats / docker-compose 的诊断规则

如果本知识库已经给出明确规则，`SKILL.md` 应优先按这些规则解释错误，再决定是否需要修改代码、交接或验证。

---

## 10. 适用范围

本知识库主要适用于 openAN 后端 e2e 场景中的以下模式：
- 本地 pytest / Maven / bats 执行，或 SSH 远程安装类场景
- registry-center、orchestration-center 等组件的服务编排（docker-compose）
- 安装 / 初始化 / 升级 / 卸载断言场景
- 依赖安装、工具链、环境变量诊断

当失败明显不属于上述模式时，应回到通用 shell / Python / Java / 容器诊断，不要机械套用本知识库。
