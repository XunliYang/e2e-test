# 评审规范

本文件是 `code-reviewer` 的审阅检查规范。主流程在「按规范审阅」步骤读取并执行；问题定级后交由 [quantitative-scoring.md](quantitative-scoring.md) 计分合入。

**默认假设**：当前变更可能含 AI 生成代码。审阅时需要考虑「AI 代码默认加查」。

---

## 必查规范

### 1. AGENTS.md 合规检查

- 检查变更是否符合仓库结构、能力边界、Frontmatter、MCP 依赖、质量门禁和文档维护要求。
- 若变更涉及 `agents/*.md` 或 `skills/*/SKILL.md`，必须检查 YAML frontmatter 是否包含 `name` 与 `description`，且描述能准确表达触发条件、适用范围和核心能力。

### 2. 计划对齐

- 对照需求、设计、Story 验收标准或 PR 描述，判断实现是否完整覆盖目标。
- 识别功能缺失、行为偏离、过度实现和未说明的兼容性变化。

### 3. 架构设计

- 判断变更是否遵循现有模块边界、依赖方向、扩展方式和项目惯例。
- 关注不必要的新抽象、跨层耦合、重复能力、公共接口破坏和迁移风险。
- **AI 加查 — 过度设计**：是否堆砌与当前需求无关的设计模式/多层抽象；遵循 YAGNI，不为臆想场景扩 scope（对应定级多为重要或轻微）。
- **AI 加查 — 上下文破坏**：改动全局配置、基类/钩子、ORM/Schema、公共接口时，是否同步调用方与契约；未改全且会导致必挂 → 严重或重要。

### 4. 代码质量

- 关注逻辑正确性、边界条件、错误处理、资源释放、并发与状态管理。
- 检查命名、结构、重复代码、复杂度和是否存在难以维护的隐式约定。
- **AI 加查 — 逻辑伪正确**：对 diff 中分支与循环，核对空值/0/极值与 `<` vs `<=`；关键路径做简短路径推演（if/else、循环终止），不要求全文逐行朗读。
- **AI 加查 — 玩具代码**：是否只覆盖最理想路径、业务常量硬编码、缺少基本错误处理或降级；与「过度设计」相反，属实现不足而非抽象过多。
- **AI 加查 — API/库幻觉**（本规范增量重点）：
  1. 列出 diff 中新增/变更的外部包 API、SDK 方法、框架钩子。
  2. 对照当前依赖声明与锁文件（如 `package.json`/`package-lock.json`、`go.mod`、`requirements.txt`/`poetry.lock` 等）确认包与版本存在。
  3. 在依赖源码、类型定义或官方文档中核对符号名与签名；**不存在或签名不匹配 → 通常严重**。
  4. 勿将「依赖版本偏旧」单独当成缺陷；仅当调用与**当前锁定版本**不兼容或不存在时开单。

### 5. 测试验证

- 检查关键路径、边界条件、错误路径和回归场景是否被覆盖。
- 评估测试断言是否有效、是否可稳定运行、是否过度耦合实现细节。
- 若缺少验证信息，明确列出建议补充的最小测试或命令。
- **AI 加查**：伪正确与幻觉高发点是否有对应用例或手工验证说明。

### 6. 性能评估

- 识别热点路径中的额外 I/O、重复计算、低效遍历、阻塞调用、缓存失效和资源泄漏。
- 对性能问题说明触发条件和可能影响，不要只给泛泛优化建议。

### 7. 安全性

- 检查注入、越权、敏感信息泄露、不安全反序列化、路径穿越、命令执行、竞态条件和依赖风险，以下几点要重点关注：
  1. 安全地从压缩包中提取文件：
     - 检查标准化路径是否落在目标目录外
     - 限制解压文件数量、大小，防止ZIP炸弹

  2. 对所有外部数据做合法性校验后再使用：
     - 外部数据（网络、用户输入、文件、环境变量等）不可信，必须校验。
     - 信任编辑跨域时必须校验。
     - 禁止直接使用外部数据直接构造格式化字符串
     - 禁止外部数据直接拼接命令参数

  3. 避免代码中包含公网地址以及秘钥等信息：
     - 禁止在代码中硬编码IP地址、域名
     - 禁止在代码中硬编码秘钥、密码等认证凭据

  4. 避免敏感信息泄露
     - 避免运行日志、操作日志中明文泄露秘钥、密码等敏感信息。
     - 用户界面中禁止直接明文显示密码等信息。

  5. 使用安全的加解密算法
     - 系统中应该使用业界公开的、标准的密码学算法。
     - 禁止使用不安全的密码算法，推荐使用强密码算法,已知的不安全密码算法如下：
       - 对称加密（分组加密）：Blowfish, DES, DESX, RC2, Skipjack, 2TDEA, TEA，3DES（加密传输协议TLS/SSH密码协议中必须禁止使用3DES，非密码协议场景必须保证密钥K1≠K2≠K3），CAST-128、IDEA
       - 对称加密（流加密）：SEAL, CYLINK_MEK, RC4
       - 哈希算法：SHA0, MD2, MD4, MD5, SHA1(数字签名、Hash-only场景),RIPEMD, RIPEMD-128
       - 非对称加密：RSA (小于 2048 bits)，ECIES (小于 224bits)，DLIES（小于2048bits)
       - 数字签名：RSA (小于2048 bits)，DSA (同X9.42标准DH，小于 2048 bits)，ECDSA(小于224bits)
       - 密钥协商（DH）：L<2048 bits，N*<224 bits
       - 密钥协商（ECDH）：ECDH(小于 224bits)
       - 息验证码）算法：HMAC-MD5
       - 协议：SSH服务所有带CBC模式的算法，TLS中带CBC模式的算法（目前TLS 1.2中含CBC的套件没有已知的攻击，业界仍被使用，不在不安全算法内），匿名算法套件

  6. 系统外开放的接口，都需要具备认证机制、鉴权机制（如果是K8S集群的资源，可以直接使用K8S的RBAC机制，不用单独再实现一套认证、鉴权机制）。
     - 系统管理面对外提供的接口，需要具备认证机制（标准协议中无认证机制的除外）
     - 系统管理面对外提供的接口，需要进行鉴权之后才能访问系统内资原
     - 系统管理面对外提供的接口，除查询类接口都需要记录操作日志

  7. 应使用安全的协议在非信任网络之间传输数据，不应使用SSL2.0、SSL3.0、TLS1.0、TLS1.1协议进行安全传输，推荐使用更安全协议TLS1.2和TLS1.3

- 对检视出来的安全问题必须给出可被利用的攻击路径或明确的安全风险说明。

### 8. 可维护性、可靠性、可读性

- 检查变更是否易于理解、定位故障、扩展和回滚，代码注释是否一致。
- 关注日志、错误信息、配置默认值、兼容策略、失败降级和文档同步。
- **AI 加查 — 注释**：删除或标出仅复述代码的注释；清除 AI 对话残留（如 “Sure, here's…”、未完成的思考片段）；注释应解释「为什么」，并与需求/设计一致时再保留。

## AI 代码默认加查（速查）

| 关注点 | 主要落入 | 取证要点 | 常见等级 |
|--------|----------|----------|----------|
| 逻辑伪正确 | 4 代码质量 | 边界与分支路径推演 | 严重 / 重要 |
| API/库幻觉 | 4 代码质量 | 锁文件 + 符号/签名核对 | 多为严重 |
| 上下文破坏 | 3 架构 / 2 计划 | 调用方与契约是否联动 | 严重 / 重要 |
| 过度设计 | 3 架构 | YAGNI，无必要抽象 | 重要 / 轻微 |
| 玩具代码 | 4 代码质量 | 缺错误路径/硬编码理想路径 | 重要 / 轻微 |
| 注释/对话残留 | 8 可维护性 | 复述型注释、AI 对话痕迹 | 多为轻微 |

同一缺陷只开一条问题，选上表「主要落入」对应必查项归类；AI 相关问题不作为单独段落输出，但仍计入问题数量，标题可加前缀如 `[AI-幻觉]` 便于识别。

## 问题分级

审阅产出的每条问题须归入以下三级之一（与量化评分共用，不得另造档位）：

| 等级 | 含义 | 合入含义 |
|------|------|----------|
| **严重** | Bug、安全问题、数据丢失风险、功能损坏；含已证实的虚假 API 调用 | 必须修复，阻塞合入 |
| **重要** | 架构问题、功能缺失、错误处理不完善、测试覆盖不足；含明显上下文破坏 | 应该修复，阻塞合入 |
| **轻微** | 代码风格、优化机会、文档润色、注释/AI 对话残留 | 建议优化，不单独阻塞 |

分级要基于实际影响。不要把偏好类意见升级为严重或重要问题。扣分数值见 [quantitative-scoring.md](quantitative-scoring.md)。
