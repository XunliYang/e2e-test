# 质量量化评分机制

本文件是 `code-reviewer` 的质量量化评分细则。主流程在完成问题列举后读取并执行；度量**变更质量能否合入**，与「评审置信度」（证据充分程度）无关，勿混入本分。

---

## 严重性与扣分

与 [review-standards.md](review-standards.md)「问题分级」使用同一套三级枚举，不得另造「致命 / 一般 / 建议」等档位。扣分见下表；等级含义以 review-standards 为准，下表补充合入与扣分。

| 等级 | 含义 | 合入含义 | 扣分 |
|------|------|----------|------|
| **严重** | Bug、安全问题、数据丢失风险、功能损坏；含虚假 API 调用、未同步的破坏性接口变更导致调用方必挂等 | **必须修复**，阻塞合入 | −15 / 个 |
| **重要** | 架构问题、功能缺失、错误处理不完善、测试覆盖不足；含明显 N+1、关键路径无超时、契约变更未改全调用方等 | **应该修复**，阻塞合入 | −7 / 个 |
| **轻微** | 风格、命名、注释冗余/AI 残留、文档润色、非关键路径的优化与过度设计倾向等 | **建议优化**，不单独阻塞 | −3 / 个 |

分级按**实际影响**，不把偏好类意见升为严重/重要。

---

## 计分规则

1. **基础分** 100；得分 = max(0, 100 − 各问题扣分之和)。
2. **计数粒度**：报告「问题」列表中每一条独立问题计 1 个，按条数扣分；每条问题只产生一次扣分（不得因「既算安全又算质量」扣两次）。
3. **已撤回 / 已说明项**：经用户确认为误报，或业务特殊性已书面说明「不修改且可接受」的项，**不计入扣分、不计入阻塞计数**。误报项应从「问题」中删除；确认不修改的项移入报告「已说明项」。

---

## 合入规则

按顺序判定，**前者优先于后者**：

1. **阻塞项优先**：存在任意未处理的 **严重** 或 **重要** 问题 → **不通过**（不论总分多少）。
2. **总分辅证**：无严重、无重要，且得分 **≥ 90** → **通过**；得分 **< 90** → **不通过**（须处理轻微项，或经用户明确接受残留轻微项后重评）。
3. **通过表述**：仅当判定为通过时，摘要/合入建议可写「建议合入」或「可以合入」；不通过时须写明阻塞原因。

禁止使用未定义的「分维度评分」（如安全维度分）。

### 决策真值表

| 未处理严重 | 未处理重要 | 得分 | 决策 |
|------------|------------|------|------|
| ≥1 | — | 任意 | 不通过 |
| 0 | ≥1 | 任意 | 不通过 |
| 0 | 0 | ≥90 | 通过 |
| 0 | 0 | <90 | 不通过 |

---

## 评分步骤（评审完成后执行）

1. 统计「问题」中未处理的严重 / 重要 / 轻微条数（不含「已说明项」）。
2. 按上表计算综合得分。
3. 按合入规则得出决策（通过 / 不通过）。
4. 若不通过：撰写阻塞原因——有严重/重要时列出等级与问题标题（最多 3 条，其余用「等共 N 条」）；仅因总分时说明「无严重/重要，但轻微项导致得分 &lt; 90」。
5. 将结果写入报告「量化评分」章节；摘要中的合入建议须与决策一致。

---

## 报告字段（写入主模板「量化评分」）

```markdown
## 量化评分

| 项 | 值 |
|----|-----|
| 综合得分 | <score> / 100 |
| 未处理问题 | 严重 <n> / 重要 <n> / 轻微 <n> |
| 决策 | 通过/不通过 |

**阻塞原因**：（仅不通过时填写；通过时省略本段）
- …
```

示例（不通过）：

```markdown
## 量化评分

| 项 | 值 |
|----|-----|
| 综合得分 | 58 / 100 |
| 未处理问题 | 严重 2 / 重要 1 / 轻微 3 |
| 决策 | 不通过 |

**阻塞原因**：存在 2 个严重问题（API Key 硬编码；XXX 读写竞态），1 个重要问题（接口变更未更新调用方）。
```
