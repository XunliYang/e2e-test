# FIT 与 DFX 场景归属判据

本文件是 FIT / DFX 场景归属的**单一事实来源**。`feature-level-test-cases-gen`、`dfx-test-cases-gen`、`test-cases-reviewer`、`test-cases-generator` 生成、评审与跨表去重时必须对照本文，禁止另起一套边界规则。

## 1. 主规则（以验证目标判定）

**以验证目标判定，不以触发操作判定。**

- 凡以**非功能设计能力**为验证目标——探针 / 日志 / 指标 / 自愈 / 性能 / 安全 / 兼容——的用例一律归 **DFX**。
- 凡以**业务功能正确性**为验证目标——服务可达、主路径走通、功能配置变更后业务生效、业务状态迁移、业务级负例被拒——的用例一律归 **FIT**。

同一触发操作（非法输入、配置变更、kill 进程、依赖不可用等）允许在两表各出现一次，但**断言焦点必须不同**：

| 表 | 允许断言 | 禁止断言（作为该条的验证目标） |
|----|----------|-------------------------------|
| FIT | 业务规格结果：响应字段/状态码、API 校验拒绝与业务错误消息、业务流程是否按规格走通 | 健康探针、ERROR 日志上下文、自愈重建、资源曲线、鉴权审计、版本兼容 |
| DFX | 非功能设计能力：health/metrics 端点、ERROR 日志与上下文、热更新机制、自愈/隔离、资源与时延、鉴权审计、兼容 | 仅重复 FIT 的业务结果（创建成功、规则生效、非法输入被拒等）且无非功能断言 |

禁止把**同一断言焦点**写成两条用例分别放入 FIT 与 DFX。步骤相似但断言不同，不算重复。

## 2. FIT 允许范围

FIT **只**保留业务功能正确性场景：

| 切面 | 含义 | 示例 |
|------|------|------|
| 部署 | 服务可启动、端口/health 就绪，主路径对象可创建 | docker compose up 后 health 返回 200，可注册业务对象 |
| 主路径 | 端到端业务走通，断言符合功能规格 | 注册 Agent 后可被查询/发现，字段与 payload 一致 |
| 功能配置变更 | 修改**业务配置**后，业务行为按新规格生效 | 更新 Agent capabilities 后查询返回新值 |
| 业务状态迁移 | 对象按业务状态机迁移（含关键非法业务迁移被拒） | Agent 已注册→在线→离线→注销按规格迁移 |
| 业务级负例校验 | 无效等价类、边界外、无权限时的**功能拒绝** | API 对非法 payload 返回 400/422 并给出业务错误消息 |
| 并发下业务正确性 | 并发操作后业务结果符合规格（无脏写、最终一致） | 并发注册不同 Agent，各注册结果独立正确 |
| 跨组件业务集成 | 材料支撑时的跨组件**业务**协同 | orchestration-center 经 registry-center 发现 Agent 并下发任务 |

## 3. DFX 允许范围（按类型）

| 简写 | 验证目标 | 允许 | 禁止（应归 FIT 或删除） |
|------|----------|------|------------------------|
| DFT | 可测试、可外部探测 | health/存活/就绪端点、metrics/状态 API、配置变更后**可被外部断言**（无需侵入） | 以「业务功能已按新配置生效」为唯一断言 |
| DFD | 可诊断、可定位根因 | 非法输入或故障注入后的 **ERROR 日志、错误上下文、无静默失败、错误指标** | 只断言「非法输入返回 400/422」而不查日志与可观测性（业务拒绝归 FIT） |
| DFS | 可运维 | compose 升级/回滚、滚动重启无中断、配置 **热加载/平滑重启机制**、优雅退出、实例扩缩 | 细化复制「改业务配置 → 业务结果变了」；把首次部署当可运维专项 |
| DFR | 可靠、自愈、隔离 | kill 进程/停止容器后重建、崩溃自愈、依赖不可用时重试/熔断/恢复、故障隔离 | 把「依赖对象不存在则业务创建失败」写成可靠性用例（功能负例归 FIT） |
| DFP | 性能、资源可控 | 稳态资源曲线、压测/长跑、内存/CPU limit、高并发不卡死、资源不足不雪崩 | 以业务主路径是否走通为唯一断言 |
| DFNS | 安全 | 未授权拦截、审计日志、TLS/加密、注入防护、权限最小化 | 仅写「无权限时业务操作被拒」且无鉴权/审计断言（功能负例归 FIT） |
| DFC | 兼容 | N-1 客户端、多语言 SDK 互通（Java↔Python）、升级共存、配置废弃策略 | 当前版本业务主路径 |

## 4. 具体场景归属（可操作）

| 场景 | 归 FIT | 归 DFX | 两边都写时的切分 | 禁止 |
|------|--------|--------|------------------|------|
| 部署 / 安装 | 服务可启动、主路径可创建 | DFS：compose 升级 / 回滚 / 扩缩容等运维过程 | FIT=首次启动就绪；DFS=升级回滚过程 | FIT 写「滚动升级无中断」；DFX 只写「启动后功能可用」 |
| 主路径 | 业务端到端按规格走通 | — | 不入 DFX | DFX 逐步复制 FIT 主路径步骤 |
| 功能配置变更 | 新配置后**业务行为**符合规格 | DFT：变更后状态可被端点/API 断言；DFS：热加载/平滑重启**机制** | FIT=业务生效；DFX=可探测或运维机制 | DFX 细化复制「改配置→业务结果」；FIT 以「无需重启」为唯一目标 |
| 业务状态迁移 | Agent/任务按业务状态机迁移 | — | 不入 DFX | FIT 把 kill 进程重建当成「状态恢复」 |
| 非法输入 / 负例 | API 校验拒绝（400/422），业务错误消息符合规格 | DFD：ERROR 日志、上下文、无静默失败、错误指标；DFNS：注入攻击拦截与审计 | FIT=业务拒绝；DFD=可诊断性 | DFX 只断言返回错误码；FIT 只断言「有 ERROR 日志」 |
| 并发 | 并发后业务结果符合规格 | DFP：高并发资源/时延/不卡死 | FIT=正确性；DFP=性能 | FIT 写压测资源曲线 |
| 业务依赖对象不存在 | 规格规定应功能失败并给出业务错误消息 | — | 不入 DFR | 写成「依赖故障恢复」 |
| 依赖服务故障注入 | — | DFR：重试/熔断/隔离/恢复；DFD：故障后可诊断 | 不入 FIT | FIT 写停止依赖后自愈 |
| kill 进程 / 停止容器 / 重启恢复 | **不归 FIT** | DFR：自动重建、自愈、故障隔离 | 不入 FIT | FIT 写进程被杀自愈或服务重启恢复 |
| 资源不足（磁盘满、内存不足） | **不归 FIT** | DFR/DFP：降级、不雪崩、limit | 不入 FIT | FIT 写资源不足降级 |
| 故障注入恢复 | 仅当注入是为触发**功能规格中的失败路径**（如开关关闭后功能不可用） | DFR/DFD：注入后自愈、隔离、可诊断 | 断言焦点必须不同 | 两表各写一条「故障注入后恢复」且断言相同 |
| 探针 / metrics | **不归 FIT** | DFT | — | FIT 写健康检查专项 |
| 安全鉴权 | 规格要求无权限时业务操作被拒（功能负例） | DFNS：401/403、审计、加密、防注入 | FIT=业务拒绝；DFNS=安全机制 | FIT 写 TLS/审计专项 |
| 多版本 / 多语言 SDK 兼容 | **不归 FIT** | DFC | — | FIT 写兼容专项 |

## 5. 错误推测法在 FIT 中的边界

FIT 使用错误推测法时，**只**补充业务级易错场景：

- 允许：空值/非法业务输入、并发下业务结果、业务依赖对象不存在时的功能拒绝、权限不足导致业务操作被拒
- **禁止**写入 FIT：重启恢复、kill 进程/停止容器自愈、资源不足降级、依赖服务故障注入与恢复、网络分区自愈（上述一律归 DFR/DFP/DFD）

## 6. 跨表重复判定

同时存在 FIT CSV 与 DFX CSV 时，按下表判定是否重复（须记入边界检查并不通过）：

| 判定 | 条件 | 处理 |
|------|------|------|
| **重复** | 触发操作相同（或同义改写）**且**断言焦点相同（都在验证业务结果，或都在验证同一非功能能力） | 删除或改写其中一条，使断言焦点回到所属表 |
| **越界** | FIT 行的验证目标属于 §3；或 DFX 行的验证目标属于 §2 且无非功能断言 | 将用例改到正确的表，或删除 |
| **合法并存** | 触发相似但断言焦点分属 §2 与 §3（例如 FIT 断言非法 payload 被拒，DFD 断言对应 ERROR 日志） | 保留；边界检查记「合法并存」 |

名称相似、步骤相似但断言不同，**不算**重复。

## 7. 生成与评审时如何执行

1. 列出候选用例后，先用 §1 主规则判定验证目标，再用 §4 表归类。
2. FIT 生成：对照 §2、§5 剔除 DFX 场景后再写入 CSV。
3. DFX 生成：对照 §3、§4 剔除 FIT 业务复制后再写入 CSV；若有 FIT 产物，禁止逐步复制其业务步骤并以业务结果为唯一断言。
4. 编排层：对两份 CSV 做 §6 交叉检查，产出边界检查报告；评审时把对方 CSV（及边界检查结论）作为对照输入。
5. 存在越界或重复 → 该范围**不通过**，须修改后复审；合法并存不构成不通过。
