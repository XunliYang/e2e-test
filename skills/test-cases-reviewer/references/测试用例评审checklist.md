# 测试用例评审Checklist

**核心原则：原子性，可重复性，可追溯性，完整性，独立性**

| 用例属性 | 要求 | 自检项 | 规则描述 | 典型问题 |
| :--- | :--- | :--- | :--- | :--- |
| **case_id** | 必须 | 编号在本仓库范围内唯一 | 【规则】用例编号在仓库范围内唯一<br>【推荐】格式 `FIT-<模块缩写>-<3位序号>` / `DFX-<模块缩写>-<3位序号>`，如 `FIT-RC-001`；模块缩写与 module 列一致 | |
| | 必须 | 编号为中/英文、数字、下划线、“-”组合，不存在特殊字符、空格 | | |
| | 建议 | 编号连续、缩写全表一致 | | |
| **type** | 必须 | 类型字段填写准确 | 【规则】FIT 表填 `FIT`；DFX 表填该条所属 DFX 类型简写：`DFT` 可测试性、`DFD` 可诊断性、`DFS` 可运维性、`DFR` 可靠性、`DFP` 性能、`DFNS` 安全性、`DFC` 兼容性；一条用例仅一种类型 | |
| **module** | 必须 | 被测模块/组件明确 | 【规则】openan 仓名（如 `registry-center`）或仓内模块名；与 case_id 模块缩写一致 | 1.描述过于笼统（如只写 `backend`） |
| **title** | 必须 | 说明测试用例的测试目的或者测试意图 | 【规则】用例名称做到简洁，短小，表达测试的意图、内容或条件的相关信息，标题不要太长，一般控制在50个中文字符内。<br>例：<br>  在xx场景下，验证XX安装是否为xx<br>  验证xx是否xx_xx场景_xx条件 | 1、名称相互包含<br>2、名称有冗余信息<br>3、名称格式不统一 |
| | 必须 | 语言简洁、明确、无二义 | | |
| | 建议 | 标题字数控制在50个中文 | | |
| | 建议 | 语法要求动宾（补）短语，可以通过"_"追加条件或原因 | | |
| **priority** | 必须 | 级别填写合理 | 【规则】等级划分准确，满足一般的比例要求<br>  P0：特性验收用例，部署就绪成功、核心功能正向主流程（DFX 表为核心可观测/可运维主路径）<br>  P1：特性基本功能用例，继承特性基本功能、需求绝大部分规格覆盖（DFX 表为关键诊断与可靠性）<br>  P2：特性复杂场景与业务级异常/负例（FIT 表仅表示业务场景优先级，**不含 DFX 用例**；探针/日志/自愈/性能/安全/兼容等写入独立 DFX 表） | |
| | 建议 | 整体审视级别占比是否合理 | | |
| **precondition** | 必须 | 对预先配置的部分进行描述，如测试环境、数据配置等信息 | 【规则】预置条件注明具体的测试环境、数据配置、当前系统的状态（软件，硬件，网络环境）<br>【规则】环境要素明确化，例如明确 compose 服务组件与版本、端口、鉴权 token、预置测试数据。<br>【规则】每一步表述语句前需要使用序号进行标识，标识采用“阿拉伯数字序号”＋“分隔符”的方式。序号从“1”开始，分隔符为：[空格/半角,/半角、] | 1、前置条件不是测试步骤<br>2、前置条件不能和测试步骤冗余 |
| | 必须 | 环境要素明确化 | | |
| | 必须 | 每步表述语句前使用序号+分隔符标识 | | |
| | 建议 | 前置条件不应该包含测试步骤，如登录、打开等操作 | | |
| | 建议 | 前置条件的步骤数不超过10步 | | |
| **steps** | 必须 | 每条测试步骤需要使用序号标识 | 【规则】每条测试步骤需要使用序号标识，编号要求“阿拉伯数字序号”＋“分隔符”<br>【规则】如要对操作结果进行检查，则在该步骤结束后加“见结果xx”，xx是“预期结果”中的编号<br>【规则】如要在连续的测试步骤完成后才判断某一个预期结果，可以在连续完成多个测试步骤的描述后再描述“见结果xx”。这种情况下，不能将连续的多个独立的测试步骤都放在一个标号中，避免内容会太冗长，应当每个独立的测试步骤都是一个独立的标号进行标识<br>【规则】如果存在明确输入，操作入口、测试参数需要在步骤详细说明 | |
| | 必须 | 每一步操作都是可执行的，无歧义的 | | |
| | 必须 | 需要检查结果的步骤结束后加“见结果xx” | | |
| | 必须 | 连续多个独立的测试步骤不能放在一个标号中，避免内容会太冗长 | | |
| | 建议 | 写明输入数据，操作入口和测试参数 | | |
| | 建议 | 测试步骤包含的步骤数不超过10步 | | |
| **expected_result** | 必须 | 每条预期结果需要使用序号标识 | 【规则】表述语句前使用序号标识，编号要求“阿拉伯数字序号”＋“分隔符”<br>【规则】表述中禁止用含二义性、模糊的描述语句（明确的数据，响应消息，界面变化）<br>【规则】每一条预期结果与其对应的测试步骤的编号建议保持一致。如一个测试步骤1对应多个预期结果，可用”见结果xx“表述<br>【推荐】预期结果中说明每一个预期结果与测试步骤的对应关系，特别是测试步骤较多的场景<br>【推荐】预期结果的描述尽量准确，具体，不要出现难以观察和判断的结果。 | 举例 |
| | 必须 | 表述中禁止用含二义性、模糊的的描述语句 | | |
| | 建议 | 预期结果与其对应的测试步骤的编号保持一致 | | |
| | 建议 | 预期结果中说明每一个预期结果与测试步骤的对应关系 | | |
| | 建议 | 描述尽量准确、具体，不要出现难以观察和判断的结果 | | |
| **language_profile** | 必须 | 每条用例标注自动化执行语言 profile | 【规则】填 `python` / `java` / `js` / `shell` 之一；默认取被测仓主语言，跨组件用例取测试落地方语言；供 `e2e-test-code-gen` 直接消费 | 1.跨仓用例错填被测仓语言<br>2.留空 |
| **component_deps** | 必须 | 跨组件依赖标注 | 【规则】无跨组件依赖填 `none`；有则填 openan 依赖仓（如 `orchestration-center`），多个用 `\|` 分隔；仅填步骤中真实交互的组件 | 1.跨组件用例漏填 none 以外依赖<br>2.填带 owner 前缀的全限定名 |
| **protocol_primitive** | 必须 | A2A-T 协议原语标注 | 【规则】涉及 A2A-T 协议的用例填 `Task-T` / `Notification-T` / `Negotiation-T` / `Authorization-T` 之一；纯 REST 用例填 `none`；禁止自造原语名 | 1.A2A-T 用例填 none<br>2.发明原语名 |
| **notes** | | 可选补充：设计方法、里程碑、校验点来源、待确认项 | 用户给了发布版本时可标注 `里程碑:vX.Y`；逐条评审不检查本列 | |
| **测试用例文件名称规范** | 必须 | 明确仓库、特性 | 【规则】规范名称（版本段可省略）：<br>特性级集成测试用例：<br>[xx版本_]<目标仓库>_<特性>特性级集成测试用例<br>DFX测试用例：<br>[xx版本_]<目标仓库>_<特性>DFX测试用例<br>例：<br>registry-center_Agent注册特性级集成测试用例<br>registry-center_Agent注册DFX测试用例 | |
| **需求符合要求** | 必须 | 需求覆盖 | 测试用例100%覆盖原始需求要求的全部功能，且无需求理解偏差；测试用例覆盖所有测试点、覆盖所有已知的用户使用场景 | |
| | 必须 | 场景覆盖 | 能够涵盖正常场景、异常场景、功能交互场景等；测试用例的目标清楚，并能满足软件质量的各个方面。FIT 与 DFX 分表时：FIT 覆盖业务功能正确性，DFX 覆盖非功能设计能力，禁止混入与跨表重复（见 FIT与DFX场景归属判据） | |
| | 必须 | 场景归属 | 【规则】以验证目标判定：业务功能正确性归 FIT；探针/日志/指标/自愈/性能/安全/兼容归 DFX。FIT 表不得含进程/容器自愈、资源不足降级、依赖故障恢复等 DFX 场景；DFX 表不得以业务结果为唯一断言复制 FIT | FIT 混入 DFX；DFX 细化复制 FIT |
| | 必须 | 跨表去重 | 【规则】同时存在 FIT 与 DFX 表时，同一触发操作且同一断言焦点不得在两表重复；断言焦点不同的合法并存允许 | 故障注入恢复等在两表各出现一次且归类不同、断言相同 |
| | 建议 | 复杂场景标注所用设计方法 | | |
| **DFX 覆盖** | 必须 | DFX 维度覆盖完整 | 【规则】所有适用的 DFX 维度均有对应用例，DFX 维度包括：<br>  DFT 可测试性、DFD 可诊断性、DFS 可运维性、DFR 可靠性、DFP 性能、DFNS 安全性、DFC 兼容性<br>【规则】不适用的 DFX 维度需说明原因 | 1、仅覆盖部分 DFX 维度<br>2、未说明不适用维度原因 |
