# 特性级集成测试用例编写指导

## 1. 定义

特性级集成测试（feature-level-integration-test），简称 FIT，旨在对特性在真实场景进行端到端验证。它围绕一个具体的业务特性，验证与之相关的多个模块或服务能否协同工作、正确实现该特性。不同于「大而全」的系统全量回归测试，也不同于「小而精」的单个接口测试，FIT 聚焦一个完整的业务功能，从用户操作触发，贯穿整个技术链路进行验证。

FIT **只验证业务功能正确性**：服务部署就绪、主路径走通、功能配置变更后业务生效、业务状态迁移、业务级负例校验。探针/日志/指标/自愈/性能/安全/兼容等非功能设计能力归 DFX，不得因「异常场景」或优先级 P2 写入 FIT 表。场景归属以 `FIT与DFX场景归属判据.md` 为准。

## 2. 设计方法

### 2.1 设计方法概览

测试用例设计应运用以下方法，并在用例中标注所采用的方法（写在「备注」列：`设计方法:xxx`）。不同方法适用于不同场景，通常需要组合使用以达到充分覆盖。

| 设计方法 | 适用场景 | 覆盖目标 |
|----------|----------|----------|
| 等价类划分 | 输入参数有明确的有效/无效范围 | 用最少用例覆盖所有输入分类 |
| 边界值分析 | 输入存在数值范围或长度限制 | 覆盖边界上、边界内、边界外的值 |
| 正交试验法 | 多个独立因子、每个因子有多个取值 | 用较少组合覆盖因子间的交互效应 |
| 状态迁移法 | 被测对象存在多个状态及状态间转换 | 覆盖所有合法和非法状态迁移路径 |
| 判定表法 | 多个条件组合产生不同动作 | 覆盖所有条件组合及对应的动作 |
| 错误推测法 | 基于经验推测业务级易错场景 | 补充其他方法未覆盖的**业务负例**（不含 DFX 自愈/资源/故障注入恢复） |
| 场景法 | 业务流程包含多个步骤和分支 | 覆盖主流程和业务级关键负例流程 |

### 2.2 等价类划分

将输入数据划分为若干等价类，从每个等价类中选取代表值作为测试数据。

- **有效等价类**：符合需求规格的输入
- **无效等价类**：不符合需求规格的输入

**应用规则：**

1. 每个有效等价类至少一条用例
2. 每个无效等价类单独一条用例（避免多个无效输入相互掩盖）

**示例：Agent 注册 payload 输入规则检验**

| 等价类 | 类别 | 代表值 | 对应用例 |
|--------|------|--------|----------|
| 合法名称（英文字母+数字） | 有效 | `agent-test-01` | 验证合法名称注册成功 |
| 合法名称（最大长度） | 有效 | 63 字符字符串 | 验证最大长度名称注册成功 |
| 空字符串 | 无效 | `""` | 验证空名称时返回 400/422 |
| 含特殊字符 | 无效 | `agent@#$` | 验证特殊字符时返回 400/422 |
| 超长名称 | 无效 | 64 字符以上 | 验证超长名称时返回 400/422 |

### 2.3 边界值分析

在等价类划分的基础上，重点测试边界上和边界附近的值。

**应用规则：**
1. 取边界值本身、刚好在边界内（边界-1）、刚好在边界外（边界+1）
2. 上下边界均需覆盖

**示例：假设单次批量注册上限为 100 条**

| 边界 | 测试值 | 预期结果 |
|------|--------|----------|
| 下边界 | 0 条 | 返回 400 参数错误 |
| 下边界+1 | 1 条 | 注册成功 |
| 上边界-1 | 99 条 | 注册成功 |
| 上边界 | 100 条 | 注册成功 |
| 上边界+1 | 101 条 | 返回 400 超过上限 |

### 2.4 正交试验法

当存在多个独立因子时，选择代表性的因子组合，避免穷举。

**应用规则：**
1. 识别所有正交因子及其取值
2. 标注因子间的交互策略：
   - **正交**：因子间存在交互影响，需要覆盖两两组合
   - **覆盖**：因子独立，仅需保证每个取值至少出现一次
3. 具体正交因子需要根据业务特性决定

**常见正交因子示例：**

| 正交因子 | 取值 | 交互策略 | 备注 |
| -------- | ---- | -------- | ---- |
| 注册渠道 | REST API / A2A-T SDK | 正交 | |
| Agent 类型 | 常驻服务 / 临时任务 | 覆盖 | |
| 鉴权方式 | 无鉴权 / API Key / mTLS | 正交 | |

### 2.5 状态迁移法

针对被测对象存在明确状态变化的场景，梳理状态迁移图，覆盖所有合法和关键非法迁移路径。

**应用规则：**
1. 绘制状态迁移图：列出所有状态和触发迁移的事件
2. 覆盖所有合法迁移路径
3. 覆盖关键非法迁移路径（验证系统拒绝非法迁移）

**示例——Agent 生命周期管理：**

```text
              ┌──────────┐
              │  未注册   │
              └────┬─────┘
                   │ 注册成功
                   v
              ┌──────────┐
        ┌─────│  已注册   │─────┐
        │     └────┬─────┘     │
   状态上报    注销 │        状态上报
   为离线         │            为在线
        │          v            │
        │     ┌──────────┐      │
        └────►│  在线◄──►│ 离线  │
              └──────────┘
```

需覆盖的迁移：
- 合法迁移：未注册→已注册、已注册→在线、已注册→离线、在线→离线、离线→在线、已注册→未注册（注销）
- 非法迁移验证：未注册 Agent 不能直接上报状态；已注销 Agent 不能再变更为在线

### 2.6 错误推测法

基于经验、历史缺陷、常见错误模式推测可能出错的**业务**场景。FIT 中的错误推测**只**覆盖业务功能正确性相关的易错点；重启恢复、资源不足、依赖服务故障注入与自愈归 DFX（见归属判据 §4–§5）。

**FIT 允许的错误推测方向：**
- 空值/null 等非法业务输入（断言 API 校验拒绝：400/422 与业务错误消息）
- 并发操作（同时操作同一业务资源后的业务结果符合规格）
- 业务依赖对象缺失（规格规定应功能失败并给出业务错误消息，不是依赖服务故障自愈）
- 权限不足导致业务操作被拒（功能负例；鉴权机制/审计日志归 DFNS）
- 大数据量下业务结果仍符合规格（资源曲线/泄漏归 DFP）

**禁止写入 FIT 的错误推测方向（一律归 DFX）：**
- 依赖组件故障注入、停止依赖进程后恢复（DFR/DFD）
- 资源不足（磁盘满、内存不足）降级或不雪崩（DFR/DFP）
- 网络异常（超时、断连、DNS 故障）下的重试/熔断/自愈（DFR）
- 服务/进程重启后的自愈与状态恢复（DFR）
- kill 进程 / 停止容器后自动重建（DFR）

## 3. 测试用例字段设计

**核心原则：原子性，可重复性，可追溯性，完整性，独立性**

16 列字段规则如下（openan 官方 15 列 + component_deps 第 5 列；表头顺序固定，与 openan-itest `docs/templates/testcases-template.csv` 一致）：

```csv
里程碑,用例名称,用例编号,模块,component_deps,需求链接,用例类型,优先级,前置条件,步骤描述,预期结果,可自动化,对应自动化用例,开发负责人,测试负责人,备注
```

### 里程碑（条件必填）

- 用户指定发布版本（如 `v26.12`）时填写；未指定则留空，禁止从材料推断
- 测试方案与用例表按版本归档（框架 §4.3.1），版本是转测与报告评审的归属依据

### 用例名称（必须）

- 简洁表达测试意图，控制在 50 个中文字符内
- 动宾（补）短语，可通过 `_` 追加条件或原因，如 `验证非法payload注册Agent_空名称`
- 语言简洁、明确、无二义
- 典型问题：名称相互包含、冗余信息、格式不统一

### 用例编号（必须）

- 编号在特性范围内唯一
- 格式：`FIT-<feature>-<topic>-<3位序号>`，如 `FIT-registry-center-agentcard-001`（框架 §6.1）
  - `feature`：特性/仓库名的小写连字符形式，与「模块」列一致（如 `registry-center`、`orchestration-center`）
  - `topic`：该用例所属功能场景的小写连字符短名（如 `agentcard`、`workflow`、`task-dispatch`）
- 仅允许英文字母、数字、连字符，不允许中文、空格与特殊字符
- 典型问题：feature/topic 大小写混用、序号不连续不重号混乱、编号与场景不对应

### 模块（必须）

- 用户指定的特性/模块正式名称（openan 仓名或仓内模块名，如 `registry-center`）
- 与用例编号的 feature 段对应；典型问题：描述过于笼统（如只写 `backend`）

### component_deps（必须）

- `none` 或步骤中真实交互的 openan 仓名（如 `orchestration-center`），多个用 `|` 分隔
- 与用例编号 feature 段区分：feature 段取被测模块，component_deps 只列依赖组件

### 需求链接（条件必填）

- 该用例对应的需求/Issue/PR 链接（如 `https://github.com/project-openan/registry-center/issues/1`）
- 用户指定或材料中含链接时填写；材料中亦无则留空并记入信息缺口清单
- 框架 §4.3.1 验收要求「需求链接齐备」，可追溯性依赖本列
- 典型问题：链接与用例场景不对应、填无意义的占位符

### 用例类型（必须）

- 主路径、部署就绪、功能配置变更、业务状态迁移填 `功能测试`
- 业务级负例、边界值、并发/幂等异常场景填 `异常测试`
- 涉及 A2A-T 协议原语（Task-T/Notification-T/Negotiation-T/Authorization-T）的用例填 `协议测试`
- 典型问题：负例误填功能测试、协议用例未标协议测试

### 优先级（必须）

- **P0**：特性验收用例——服务部署就绪、核心功能正向主流程
- **P1**：特性基本功能用例——基本功能与绝大部分规格覆盖、并发/幂等下业务正确性
- **P2**：特性复杂场景与业务级异常/负例（FIT 表仅表示业务场景优先级，**不含 DFX 用例**；探针/日志/自愈/性能/安全/兼容等写入独立 DFX 表）
- 建议整体审视级别占比是否合理

### 前置条件（必须）

- 描述预先配置的环境、数据与系统状态（软件版本、硬件、网络环境）
- **环境要素明确化**：明确 compose 服务已启动的组件与版本、端口、鉴权 token、预置测试数据等
- 每一步表述前用序号标识：`阿拉伯数字` + `、`（或空格/半角逗号），从 1 开始
- 前置条件**不是**测试步骤：不含登录、调用等操作；步骤数不超过 10 步
- 典型问题：前置条件写成测试步骤、与测试步骤冗余

### 步骤描述（必须）

- 每条步骤使用序号标识：`阿拉伯数字` + `、`
- 需要对操作结果进行检查的步骤，结束后加 `见结果N`，N 是「预期结果」中的编号
- 每个独立步骤独立编号；连续多个独立步骤不能合并在一个标号中
- 写明操作入口、接口路径与测试参数
- **末步必须为清理动作**（框架 §6.3）：删除本用例创建的测试数据、Agent、临时配置或停止拉起的服务，保证用例独立可重复
- 步骤数建议不超过 10 步
- 典型问题：步骤不可执行、有歧义、缺少输入数据、缺少清理动作

### 预期结果（必须）

- 每条预期结果使用序号标识：`阿拉伯数字` + `.`
- 禁止二义性、模糊描述；用明确的数据断言：HTTP 状态码、响应体字段及取值、查询结果、业务对象状态
- 预期结果与对应步骤编号建议保持一致；一步对应多个结果时用 `见结果N` 说明对应关系
- 描述准确、具体，不出现难以观察和判断的结果；清理步骤须给出可判定断言（如再次查询返回 404、容器不存在）
- 典型问题：`功能正常`、`无异常` 之类不可判定的表述

### 可自动化（必须）

- 填 `是`/`否`
- **P0/P1 必须为 `是`**（框架 §8.1 TRR 准入：P0/P1 用例通过率 100% 且要求自动化）；P2 可为 `否`，须在备注说明原因
- 典型问题：P0/P1 填「否」且无备注说明

### 对应自动化用例（留空）

- 生成阶段留空；`e2e-test-code-gen` 生成测试代码后回填 `<测试文件路径>::<测试函数名>`，保证失败可回溯

### 开发负责人 / 测试负责人（条件必填）

- 用户指定时填写；未指定留空，禁止推断占位

### 备注（必填键 + 可选补充）

各键用 `；`（或 `;`）分隔，键值内多个取值用 `|`：

- `设计方法:xxx`：按 §2 要求标注所采用的设计方法（可多个，用 `|` 分隔）
- `正交因子:因子A=值1|因子B=值2`：正交试验用例标注因子取值
- `language_profile:python|java|js|shell`：**每条必填**；默认取被测仓主语言，跨组件用例取测试落地方（编写测试代码的仓库）语言；供 `e2e-test-code-gen` 按 profile 直接消费，写错会导致测试代码生成选错技术栈
- `component_deps`（第 5 列独立列）：**每条必填**；无跨组件依赖填 `none`，有则填步骤中真实交互的 openan 仓（如 `orchestration-center`），多个用 `|` 分隔；禁止填带 owner 前缀的全限定名；不写入备注
- `protocol_primitive:none|Task-T|Notification-T|Negotiation-T|Authorization-T`：**每条必填**；涉及 A2A-T 协议的用例填对应原语，纯 REST 用例填 `none`；禁止自造原语名
- `环境:docker-compose|with-workload-cluster|online|offline`：**每条必填**（框架 §6.4 environment 维度、§4.3.1 用例必须标注环境）：按用例真实运行环境填写（本地 compose 环境填 `docker-compose`），供 CI 环境过滤
- `执行策略:smoke|full|slow`：**每条必填**（框架 §6.4 execution 维度）：P0 核心验收填 `smoke`（PR CI 执行），常规 P1/P2 填 `full`（日构建执行），长稳/压测等耗时场景填 `slow`
- 材料差异、待确认项、不可自动化原因等补充说明
